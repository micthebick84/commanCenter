# 배포 후 재검증(e2e)과 같은 브랜치 수정 요청 설계

2026-11-03 · 초안(사용자와 대화로 정함 — 표의 "누가"가 `사용자`인 것만 사용자 결정, 나머지는 설계자 판단) · 선행: `2026-09-23-remote-public-deploy-dns-design.md`, `2026-10-15-implementation-mode-selection-design.md`, `2026-10-28-deploy-prebuild-design.md`

## 1. 왜

라이나 생명 작업 #20~#23(2026-11-02~03)이 모두 `배포완료`였지만 실제로는 쓸 수 없었다. 사람이 열어 보고서야 알았다.

| 증상 | 원인 | 지금 헬스체크가 못 잡은 이유 |
|---|---|---|
| 첫 화면이 오류 JSON | JVM 기본 로케일 `en` → `NoSuchMessageException`(PR #119로 고침) | 응답이 오면(404 제외) 통과 |
| 로그인 실패(비밀번호는 맞음) | Traefik이 X-Forwarded-For에 `172.18.0.1`을 덧붙여 앱이 IP 칸에 못 넣음(PR #120으로 고침) | 로그인을 안 해 봄 |
| #20에서 `트래픽기간분석 > 장기분석`, `수신자그룹 > 대상장비 탭` 화면이 안 나오거나 그리드 로딩이 끝나지 않고 갱신이 안 됨 | 미조사(이 설계의 범위 밖) | 화면을 안 열어 봄 |

지금 헬스체크(`LocalDockerTarget`)는 컨테이너 생존과 `readinessPath`의 HTTP 응답(404면 기동 실패 문구 확인)만 본다. 그리고 `배포완료`에서 "이 브랜치에서 이어 고쳐 달라"로 돌아가는 길이 없다. 지금 있는 `구현 재시도`는 `구현실패`에서만 되고, 브랜치를 `-rN`으로 새로 따서 처음부터 다시 짠다.

이 기능은 두 가지를 더한다.
1. **재검증**: 배포완료 직후 실제 브라우저로 배포 주소에 들어가 작업이 바꾼 화면을 열고 눌러 본다.
2. **수정 요청**: 재검증이나 사람이 찾은 문제를 **같은 브랜치에서 이어 고치는** 구현으로 되돌린다. 고친 뒤에는 자동으로 재배포하고 다시 재검증한다.

## 2. 목표 · 비목표 · 반목표

**목표**
- 재검증을 켠 레포의 작업은 배포완료(최초 배포·재배포 모두)마다 재검증이 자동으로 한 번 돈다. 결과(항목별 통과·실패, 근거, 스크린샷)는 작업 상세에서 본다.
- 재검증이 문제를 찾으면 작업 상세에 "수정 요청"이 보인다. 누르면 발견 내용이 미리 채워진다. 사람이 직접 찾은 문제도 같은 버튼으로 적어 보낸다(재검증이 없거나 통과여도 된다).
- 승인된 수정 요청은 작업의 기존 브랜치(`task.head_branch`) 위에서 구현되고 같은 PR/MR에 커밋이 쌓인다. 그다음 같은 env로 자동 재배포 → 자동 재검증.
- 재검증을 켜지 않은 레포의 배포·구현 흐름은 지금과 같다.

**비목표**
- 작업 #20 화면 문제 자체를 고치는 일(그 작업의 수정 요청으로 처리).
- 배포마다 DB를 복제·격리하는 일. 배포본은 WAR 안에 고정된 개발 DB를 그대로 읽고 쓴다(§5.4).
- 종료(`작업종료`)된 작업을 다시 여는 일. 종료 때 브랜치가 병합·삭제되므로 그 뒤의 버그는 새 작업으로 등록한다(§6.5).
- 원격 워커(10.1.1.75·Mac)에서 재검증을 돌리는 일. 배포를 맡는 이 PC 워커만 돈다.
- 수정 요청 없이 문제를 자동으로 고치는 일. 항상 사람이 요청하고 관리자가 승인한다.
- 모바일 화면 크기 검증, 성능·부하 시험, 비 HTTP 앱.

**반목표** (이렇게 되면 실패)
- 재검증이 **원래 있던 데이터**를 수정·삭제하는 것. 알림·메일·SMS 발송, 장비 명령(설정 적용·재부팅·SNMP set 등), 사용자·권한·비밀번호 변경처럼 **배포본 밖으로 영향이 나가는** 동작을 누르는 것.
- 재검증 계정 비밀번호가 DB(암호문 칸 말고)·배포 로그·재검증 결과·스크린샷·작업 이력·PR 본문 어디에든 평문으로 남는 것.
- 수정 구현이 브랜치를 새로 따거나 base에서 다시 시작해, 작업이 이미 바꾼 코드가 사라지는 것. 같은 브랜치를 force-push로 덮는 것.
- 재검증 실패가 종료를 막거나 상태를 `배포실패` 등으로 바꾸는 것. 재검증은 **유도**이고 작업 상태는 `배포완료` 그대로다.
- 재검증이 끝나지 않고 토큰을 계속 쓰는 것. 또 자동 반복(수정 → 재배포 → 재검증 → 수정…)이 사람 승인 없이 이어지는 것.

| 수정 회차를 받는 워커 | 구현 워커 모두(원격 포함). 구버전 jar는 claim 가드로 막는다. 구현에는 스크린샷이 아니라 **글**(근거·오류 발췌)만 넘긴다 | 설계자 |

## 4. 흐름

```
[배포완료] ──(자동: 카탈로그 재검증 켜짐)──→ 재검증 실행(대기 → 진행 → 통과|문제 있음|오류)   ※ 작업 상태는 배포완료 그대로
                                         └─ 등록자·관리자 "다시 돌리기"로도 시작
[배포완료|배포중단됨|배포실패] ──(등록자 수정 요청)──→ [수정승인대기] ──(관리자 승인)──→ [구현대기](수정 n회차)
[배포완료|배포중단됨|배포실패] ──(관리자 수정 요청)──────────────────────────────────→ [구현대기](수정 n회차)
[수정승인대기] ──(관리자 반려 / 등록자 철회)──→ 직전 상태(배포완료|배포중단됨|배포실패)
[구현대기](수정) ──(워커 claim)──→ [구현중] ──┬→ (같은 브랜치에 push) → [배포대기](자동) → [배포중] → [배포완료](회차 닫힘) → 재검증
                                              │                                                  └→ [배포실패](회차 닫힘)
                                              └→ [구현실패](수정) ──(관리자 구현 재시도)──→ [구현대기](같은 회차, 같은 브랜치)
                                                                  └─(관리자 수정 중단)──→ [PR생성](회차 닫힘, §7.1)
```

- **수정 회차가 열려 있는 동안**은 `수정승인대기`, 회차의 `구현대기`·`구현중`·`구현실패`, 자동 재배포의 `배포대기`·`배포중`이다. 회차가 닫힌 뒤의 `배포완료`·`배포실패`·`PR생성`은 보통 작업과 같다. 재배포·중지·종료 요청·다음 수정 요청이 모두 된다(상한 안에서).
- `배포실패`에서도 수정 요청을 받는다. 수정이 빌드를 깨뜨려 자동 재배포가 실패한 경우, 또는 코드 때문에 배포가 실패한 경우를 고치기 위해서다. 브랜치(`head_branch`)가 없는 작업은 받지 않는다.
- 회차가 열려 있는 동안 기존 컨테이너·공개 주소는 유지한다(GC 보호 목록에 회차 상태를 넣는다). 고치는 동안에도 사람이 이전 배포를 볼 수 있게 하기 위해서다. 자동 재배포가 기존 컨테이너를 교체한다.

- 새 상태는 `수정승인대기`(enum 예: `FIX_REVIEW`) 하나다. 나머지는 기존 상태를 쓰고, 지금 구현이 수정 회차인지는 작업의 회차 값(§8)으로 구분한다.
- `수정승인대기`는 `종료승인대기`와 모양이 같다. 직전 상태로 되돌아가고, 그동안 종료 요청·재배포·중지는 받지 않는다(`배포중단됨`에서 요청한 경우도 같다).
- 수정 회차의 `구현중`에서 구현이 성공하면 `PR생성`에 머물지 않고 바로 `배포대기`로 간다. 상태 이력에는 `PR생성`을 거쳤다는 줄을 남겨도 되고 안 남겨도 된다(빌더 판단). 다만 화면의 상태 흐름이 헷갈리지 않아야 한다.

## 5. 재검증

### 5.1 시작·claim

- 워커가 배포 성공을 보고해 API가 `배포완료`로 바꿀 때, 그 작업 카탈로그의 재검증이 켜져 있고 로그인 계정이 저장돼 있으면 재검증 실행 1건을 `대기`로 만든다.
  - 계정이 없으면 만들지 않는다. 작업 상세에 "재검증 계정 미등록"으로 보인다.
  - 카탈로그가 없는 작업(`repo_catalog_id` null)은 끈 것으로 본다.
- 등록자·관리자의 "다시 돌리기"는 작업이 `배포완료`이고 진행 중(대기·진행) 실행이 없을 때만 된다.
- 워커는 새 kind(예: `VERIFY`)로 실행을 claim한다. **명시적으로 `WORKER_KINDS`에 이 kind를 넣은 워커만** 받는다. kind 목록이 빈 워커(지금 `win-worker-1`, 모든 kind)는 받지 않는다.
- 이 PC에 재검증 전용 워커 프로세스를 하나 더 띄운다(예: `WORKER_ID=win-verify-1`, `WORKER_KINDS=verify`, 같은 jar).
  - 지금 워커 루프는 직렬이다. 같은 루프에 넣으면 SDD 구현(최대 240분) 뒤에서 재검증이 기다리고, 재검증 30분 동안 배포·중지·종료가 밀린다.
  - `start-public.ps1`·`stop-public.ps1 -Only`·기동 정합·하트비트(`com.worker_heartbeat`)에 새 이름을 더한다.
  - 원격 워커에는 넣지 않는다.
- 회수는 `진행`만 본다. `대기`는 회수하지 않는다. 재검증 워커의 하트비트가 없으면 화면에 "재검증 워커 없음"을 보인다.
- 실행이 `취소됨`이 되면 워커가 실행 중에 주기적으로(예: 15초) 실행 상태를 확인한다. 취소면 claude·브라우저 프로세스 트리를 끝내고 정리한다.
- 실행에는 그때의 `head_sha`·`deploy_url`을 박제한다. 실행 도중 작업이 재배포·중지·수정 요청·종료로 넘어가면 그 실행은 `취소됨`으로 끝난다. 워커의 늦은 보고는 결과만 남기고 화면에는 "지난 배포의 결과"로 표시하거나 버린다(빌더 판단, 단 최신 결과로 보이면 안 된다).
- 회수: `진행`이 상한 + 10분(40분)을 넘으면 API가 `오류(중단됨)`로 끝낸다. 자동으로 다시 돌리지 않는다(토큰 낭비 방지). 사람이 "다시 돌리기"를 누른다.

### 5.2 워커가 Claude에게 주는 것

- 배포된 커밋(`head_sha`)의 읽기 전용 worktree. 배포 worktree를 재사용하거나 새로 만든다(빌더 판단). 끝나면 지운다.
- 작업 제목·설명(요건), 확정 플랜, 첨부(렌더링된 텍스트·이미지가 있으면 그것), 바뀐 파일 목록과 diff(작업 base 브랜치와 `head_sha`의 merge-base부터 `head_sha`까지 — `task`에는 base 커밋 칸이 없다), 이전 수정 요청 본문(회차가 있으면).
- 접속 주소 = `task.deploy_url`(공개 주소). 사람이 쓰는 경로(Cloudflare → Traefik)를 그대로 지나야 XFF 같은 문제가 잡힌다.
- 로그인 아이디·비밀번호·로그인 메모(카탈로그). 비밀번호를 다루는 규칙은 §5.5.
- 시험 데이터 이름 접두사 `e2e-t{작업 id}-v{실행 id}-`와 §5.4 규칙.
- 도구: 브라우저 조작(Playwright)과 worktree 읽기(Read·Grep·Glob)만 준다. 파일 쓰기·셸·git·docker는 주지 않는다.
  - 브라우저 조작 방법(Playwright MCP stdio 서버를 `--strict-mcp-config`로 붙이기 vs Claude가 Playwright 스크립트를 쓰고 워커가 실행)은 빌더가 정한다.
  - 어느 쪽이든 headless, 버전 고정, 워커 PC의 기존 Chromium 사용, 스크린샷은 워커가 정한 출력 폴더로 모은다.
- 모델·effort: 워커 설정(예: `VERIFY_MODEL`). 기본값은 빌더 판단(비용·속도 기준으로 Sonnet 계열 권장).

### 5.3 Claude가 하는 일과 결과 형식

1. **시나리오 먼저**: 요건과 diff에서 확인할 항목 목록을 만든다. 항목마다 이름, 메뉴 경로/URL, 할 동작, 기대 결과, 쓰기 여부를 정한다. 공통 항목(로그인 성공, 로그인 뒤 첫 화면이 정상)을 항상 맨 앞에 둔다.
2. **실행**: 항목마다 화면을 열고 동작한 뒤 판정한다.
   - **실패**: 화면이 정해진 시간(예: 30초) 안에 그려지지 않음 · 로딩 표시(스피너·그리드 로딩 오버레이)가 사라지지 않음 · 그 화면에서 난 콘솔 오류나 HTTP 5xx · 오류 JSON·오류 페이지가 보임 · 요건의 기대 결과가 안 보임(예: 작업 20이면 그리드 필터가 기본으로 켜져 있지 않음).
   - **건너뜀**: 판단할 수 없거나 §5.4 때문에 누를 수 없는 경우. 이유를 적는다.
   - 실패한 항목마다 스크린샷 1장 이상. 통과한 항목은 대표 1장(선택).
3. **정리**: 만든 시험 데이터를 지우고, 남은 게 없는지 목록 화면에서 확인한다. 못 지운 게 있으면 "시험 데이터 정리 실패" 항목을 실패로 남긴다(이름·화면).
4. **보고**: 마지막 출력을 정해진 JSON으로 낸다. 실행 요약, 항목 배열(이름, 경로, 동작, 기대, 결과 `PASS|FAIL|SKIP`, 근거 문장, 콘솔 오류·HTTP 상태 발췌, 스크린샷 파일 이름), 남은 시험 데이터가 들어간다. 워커가 검증해 API로 보낸다. JSON이 깨지면 실행은 `오류`.

실행 결과 상태는 이렇게 정한다.
- **통과**: FAIL 0건.
- **문제 있음**: FAIL 1건 이상. 로그인 실패도 여기 들어간다. 근거에 "계정이 맞는지 확인"을 함께 적는다. 앱 버그인지 계정 문제인지 재검증이 가를 수 없기 때문이다.
- **오류**: 재검증 자체가 못 돎. 시간 초과, 브라우저 기동 실패, claude 실패, 결과 형식 오류, 배포 주소 무응답이 해당한다.

토큰 사용은 `task_stage_usage`의 새 stage(예: `VERIFY`)에 누적한다.

### 5.4 데이터 규칙(프롬프트에 그대로 넣는다)

- 기본은 화면을 열어 보기만 한다. 등록·수정·삭제는 **작업이 바꾼 기능**일 때만 한다. 판단은 요건과 diff로 한다.
- 쓰기를 할 때는 재검증이 직접 만든 데이터만 대상으로 한다. 이름(또는 식별 칸)에 접두사 `e2e-t{id}-v{run}-`를 붙여 만든 뒤 수정·삭제한다. 원래 있던 행은 저장 버튼도 누르지 않는다.
- 다음은 어떤 경우에도 누르지 않는다.
  - 알림·메일·SMS·메신저 발송과 그 "시험 발송"
  - 장비에 보내는 명령(설정 적용·배포·재부팅·SNMP set·스크립트 실행)
  - 사용자·권한·비밀번호·계정 상태 변경
  - 일괄 삭제·가져오기·초기화
  - 외부 시스템 연동 실행
  - 결제·라이선스
- 누를지 애매하면 누르지 않고 `SKIP`으로 이유를 적는다.
- 이 규칙은 기술적으로 강제할 수 없고 프롬프트로만 지킨다. 사용자는 개발 DB에 시험 데이터를 넣었다 지우는 것까지 허용했다. 그 밖으로 나간 경우를 찾을 수 있도록 실행 결과에 **눌러 본 쓰기 동작 목록**을 남긴다.

### 5.5 비밀번호

- 저장: 카탈로그 칸에 `DbSecretCipher`와 같은 방식(AES-256-GCM, `app.db-secret.key`·`salt`)으로 암호화한다.
  - 키가 없으면 관리 화면에서 비밀번호 칸이 꺼지고, 그 레포 재검증은 "계정 미등록"으로 처리한다.
  - 응답에는 "저장됨" 여부만 싣는다. 관리 화면에서 비워 두면 기존 값이 유지된다.
- 전달: 워커 API claim 응답으로만 평문을 보낸다(워커 키 인증 경로). 워커 로그·배포 로그·API 로그에 찍지 않는다.
- Claude에게: 가능하면 비밀번호 평문이 Claude 대화에 들어가지 않게 한다. 빌더가 아래 방법을 확인해 고른다.
  - 브라우저 도구의 비밀값 치환 기능(Playwright MCP의 secrets 파일 같은 기능이 지금 버전에 있는지 확인)
  - 워커가 로그인 단계만 직접 수행하고, 로그인된 브라우저 상태(storage state)를 Claude에게 넘김
  - 어느 쪽도 안 되면 프롬프트로 넘기되, 결과·로그에 나오면 워커가 `***`로 가린다
- `claude -p`가 워커 PC에 남기는 세션 기록(`~/.claude/projects`)에 비밀번호가 남을 수 있다. 남는 방식이면 재검증 세션 기록 폴더를 실행 뒤 지운다(빌더 판단, 기존 구현 세션의 기록 정책과 맞출 것).

### 5.6 스크린샷 저장

- 워커가 실행 끝에 API로 올린다. 종료 산출물 업로드(`PUT /worker/tasks/{id}/artifact`)와 같은 원시 본문 방식이다.
- API는 트랜잭션 밖에서 `attachments/task-{id}/verify/{run id}/`에 쓴다. 작업 소프트 삭제 30일 뒤 첨부 정리 잡이 함께 지운다.
- 상한: 실행당 40장, 장당 2MB(넘으면 줄이거나 버리고 결과에 적는다). 화면에서는 등록자·관리자만 본다(기존 첨부와 같은 권한).
- 로그인 화면 스크린샷에 입력한 비밀번호가 보이지 않는지 확인한다(password 입력칸은 가려지지만, 메모·아이디 칸에 잘못 넣은 경우를 대비해 로그인 단계는 입력 전·후 스크린샷을 찍지 않아도 된다).

## 6. 수정 요청

### 6.1 내는 사람·조건

- 등록자 또는 관리자. 다음 조건을 모두 만족할 때만 낼 수 있다.
  - 작업이 `배포완료`·`배포중단됨`·`배포실패` 중 하나다.
  - `head_branch`가 있다.
  - 열린 수정 회차가 없다.
  - 소프트 삭제되지 않았다.
- 본문(필수, Markdown)을 적는다. 화면은 최근 재검증의 FAIL 항목(이름·경로·근거·스크린샷 링크)으로 본문을 미리 채운다. 사람이 빼거나 보탤 수 있다.
- 어느 재검증 실행에서 왔는지 링크(선택)를 붙인다. 재검증 없이 사람이 쓴 요청도 된다.

### 6.2 승인

- 등록자가 내면 `수정승인대기`가 된다. 승인하면 `구현대기`, 반려(사유)하면 직전 상태로 간다. 등록자는 승인 전에 철회할 수 있다(직전 상태).
- 관리자는 승인 때 구현 방식을 **직접·리뷰** 중에서 고른다. 기본은 리뷰다.
  - SDD는 확정 플랜의 `### 작업 N`마다 서브에이전트를 돌리므로, 수정 회차에서 쓰면 원래 플랜 전체를 다시 구현하게 된다(§2 반목표). 그래서 고를 수 없게 한다.
  - 리뷰 방식의 "계획 범위"는 이번 수정 요청 본문이다. 원래 플랜이 아니다.
  - 작업의 `implementation_mode`는 바꾸지 않는다. 회차의 방식은 수정 요청 기록에 둔다.
- 관리자가 내면 승인 단계 없이 바로 `구현대기`가 된다. 구현 방식은 요청 다이얼로그에서 고른다.
- 상태 이력과 수정 요청 기록에 누가·언제·무엇을 남긴다.

### 6.3 회차 상한

- 작업당 승인된 수정 요청은 최대 `app.task.fix-request-max-rounds`(기본 3)회다.
- 다 쓰면 수정 요청 버튼 대신 "새 작업으로 등록" 안내를 보인다(§6.5).
- 반려·철회된 요청은 회차에 세지 않는다.

### 6.4 동시성

- 수정 회차가 열려 있는 동안(§4의 상태들)에는 종료 요청·재배포·중지·두 번째 수정 요청을 받지 않는다(409).
- 회차가 닫힌 뒤에는 막지 않는다. 자동 재배포가 `배포실패`로 끝났으면 보통 작업처럼 재배포·중지·수정 요청이 된다.
- 종료 요청은 지금 규칙(`TaskCloseService`의 `배포완료|배포중단됨`)을 그대로 따른다.
- 상태를 바꾸는 진입점은 기존처럼 `findActiveByIdForUpdate`로 잠근다.

### 6.5 종료된 작업·상한을 넘은 작업

- "이 내용으로 새 작업 등록"을 보인다. 작업 등록 화면을 미리 채워 연다(질문 세션의 `taskPrefillFromQuestion`과 같은 방식).
  - 채우는 값: 같은 레포, 제목 `[작업 {id} 후속] …`, 본문은 발견 내용과 원래 작업 링크.
  - 브랜치: 종료된 작업이면 base 브랜치(이미 병합됨)를 쓴다. 상한을 넘은 미종료 작업이면 등록 화면에서 base를 그대로 두되, "원래 작업의 변경이 아직 병합 전"이라는 안내를 붙인다(브랜치 선택은 기존 등록 화면 기능 그대로).

## 7. 같은 브랜치에서 이어 구현

- claim 응답의 구현 정보에 수정 회차(번호, 요청 본문, 이어 갈 브랜치 `head_branch`, 기대 head `head_sha`, 회차의 구현 방식)를 싣는다. 회차가 없으면 지금 구현과 같다.
- **구버전 워커 차단**: 참조 repo의 `supports=refRepos`처럼 워커가 `supports`에 새 값(예: `fixRounds`)을 보내야만 수정 회차 구현을 내준다.
  - 구버전 jar는 회차 필드를 버리고 base에서 `-rN` 브랜치를 새로 따기 때문이다(§2 반목표).
  - 원격 워커(10.1.1.75·Mac)는 jar를 갱신하면 받는다.
- 워커:
  - 대상 캐시를 fetch하고 `origin/{head_branch}`에서 worktree를 만든다(새 브랜치를 따지 않는다).
  - 원격 head가 `head_sha`와 다르면 원격 head를 쓴다. 사람이 MR에 직접 push한 경우다. 다르다는 사실은 이력과 PR 본문에 남긴다.
  - 참조 repo·구현 방식·상한은 지금 구현과 같다.
- 프롬프트: 원래 요건·플랜 + "이 브랜치에는 이미 구현이 있다. 처음부터 다시 짜지 말고 아래 문제만 고친다" + 수정 요청 본문 + 이전 회차 요청(있으면).
  - 스크린샷은 넘기지 않는다. 지금 구현 claim에는 첨부를 넘기는 경로가 없고, 원격 워커는 API PC의 파일을 못 읽는다.
  - 대신 수정 요청 본문에 재검증의 근거 문장·콘솔 오류·HTTP 상태 발췌를 글로 담는다. 화면이 미리 채운다.
  - 스크린샷 전달은 후속 과제다(§14).
- 커밋·push: 같은 브랜치에 fast-forward push만 한다(force 금지). PR/MR은 새로 만들지 않는다.
  - PR/MR 본문 끝에 `## 수정 {n}회차` 절(요청 요약·커밋)을 덧붙인다.
  - 기존 GitHub/GitLab 갱신 경로가 없으면 본문 갱신은 생략하고 이력에만 남겨도 된다(빌더 판단).
  - `head_sha`를 새 커밋으로 바꾼다.
- `implementation_attempt`와 브랜치 `-rN` 규칙은 건드리지 않는다. 수정 회차가 있는 `구현실패`에서 관리자가 `구현 재시도`를 누르면 **같은 회차를 같은 브랜치에서 다시** 돈다. 재시도 다이얼로그에 이 차이를 보인다.
- 중간에 끝나 남은 변경을 `wip:` 커밋으로 push하는 기존 동작은 같은 브랜치에서 그대로 둔다. 다음 재시도가 그 위에서 이어 간다.
- 성공하면 API가 저장된 `task.envVars`로 `배포대기`를 만든다. 재배포와 같은 경로를 쓰고, 이력 사유는 `수정 {n}회차 구현 완료 → 자동 재배포`다.
- 배포는 브랜치 끝을 빌드한다. 자동 재배포 전에 `head_sha`가 push한 커밋으로 바뀌어 있어야, 종료 병합(`head_sha` 고정)과 배포된 코드가 맞는다.
- **재큐가 브랜치를 지우면 안 된다**: `Task.prepareImplementationRequeue()`는 `head_branch`·`head_sha`·PR 정보를 비운다. 이 메서드는 `구현 재시도`(`TaskService.retryImplementation`)와 재기동 재큐(`TaskRecovery`)가 부른다.
  - 수정 회차에서는 두 경로 모두 이 정보와 `implementation_attempt`를 그대로 두는 별도 준비를 쓴다.
  - 같은 회차의 늦은 보고(재기동 전 시도의 결과)를 가려낼 기준이 필요하다. 회차 번호 + 회차 안 시도 번호 등으로 정하는 건 빌더 판단이다.

### 7.1 수정 중단

- 수정 회차의 `구현실패`에서 관리자는 `구현 재시도` 대신 `수정 중단`을 고를 수 있다.
- 결과:
  - 회차가 닫힌다(실패한 회차로 센다).
  - `head_sha`를 그 브랜치의 원격 끝으로 맞춘다. `wip:` 같은 일부 커밋이 push됐을 수 있기 때문이다.
  - 상태는 `PR생성`이 된다.
- 이유: 브랜치에는 배포되지 않은 커밋이 있을 수 있다. 그런데 force-push는 반목표다. 그래서 "직전 배포 상태로 되돌리기"는 하지 않는다. 대신 사람이 `PR생성`에서 보통 배포(브랜치 끝)를 다시 누르게 한다. 커밋이 없었다면 같은 코드가 다시 배포될 뿐이다.
- 이 경로에는 자동 재배포가 없다.

## 11. 배포 순서

1. API(V38): 기능은 카탈로그에서 켜기 전까지 꺼진 것과 같다.
2. 이 PC 워커: 진행 중 구현·배포가 없을 때 재기동한다(`supports=fixRounds`).
3. 원격 워커 2대 jar 갱신. 갱신 전까지는 수정 회차를 이 PC 워커만 받는다.
4. 이 PC에 재검증 전용 워커 추가. 브라우저 도구를 설치하고, `public.env`와 기동·정지 스크립트에 새 서비스를 넣고, 작업 스케줄러로 기동한다.
5. 프론트: `.output`을 재빌드한다.
6. 관리 화면에서 레포(예: netis-v6.8 카탈로그 8)의 재검증을 켜고 계정을 넣는다. 비밀번호는 관리자가 직접 넣는다. 채팅·커밋·문서에 적지 않는다.
7. 첫 확인: 작업 #20 같은 배포완료 작업에서 "다시 돌리기". 장기분석·대상장비 탭 증상이 `문제 있음`으로 잡히는지, 시험 데이터가 남지 않는지 본다.

재검증 전용 워커가 없거나 꺼져 있으면 재검증 실행은 `대기`에 머문다(회수하지 않는다). 화면에는 하트비트로 "재검증 워커 없음"을 보인다. 워커가 뜨면 그때 돈다.

## 12. 시험

- API: 상태 전이(수정 요청 등록자·관리자·반려·철회·상한·동시성 409), 재검증 실행 생성 조건(카탈로그 꺼짐·계정 없음·reconcile 복구 제외), 늦은 보고·취소, 회수, 비밀번호가 응답·로그에 안 나옴, 자동 재배포 env 유지. Testcontainers 기존 방식.
- 워커: 결과 JSON 검증(깨짐 → 오류), 비밀번호 가리기, 취소 신호에 claude 종료, 같은 브랜치 worktree·fast-forward push·force 금지, 원격 head가 앞선 경우, 수정 회차 `구현 재시도`·재기동 재큐가 브랜치·`head_sha`를 지우거나 `-rN`을 만들지 않음. claude·브라우저는 가짜로 둔다.
- API 추가: `supports=fixRounds` 없는 워커에게 수정 회차를 안 줌, `수정 중단` → `PR생성`·`head_sha` 갱신, `배포실패`에서 수정 요청, 회차가 닫힌 뒤 409가 풀림, 회차 동안 GC 보호.
- 프론트: 카드·다이얼로그 단위 시험(vitest). `npm run lint`의 경고를 늘리지 않는다.
- 수동: §11의 7.

## 13. 빌더에게 맡긴 것

- 재검증 claim을 기존 claim 엔드포인트에 넣을지, 따로 둘지(작업 상태가 아니라 실행 상태로 큐를 본다는 점만 지킬 것).
- 브라우저 조작 방식(MCP vs 스크립트)과 비밀번호를 Claude 대화 밖에 두는 방법(§5.5)의 최종 선택.
- 프롬프트 문구, 항목별 대기 시간, 스크린샷 해상도.
- 화면 배치와 문구. `PR생성`을 거친 이력 표시 여부.
- 시험 데이터 접두사를 넣을 수 없는 칸(숫자만 등)에서의 식별 방법. 식별할 수 없으면 그 쓰기 시험은 SKIP.

## 14. 남은 문제·후속

- 재검증이 금지 동작을 눌렀는지 사후에 확인할 방법은 "눌러 본 쓰기 동작 목록"뿐이다. 첫 몇 번은 사람이 결과를 같이 볼 것.
- 개발 DB를 다른 사람도 쓰면 재검증의 시험 데이터가 잠깐 보인다(접두사로 구분). 격리 DB는 후속 과제다.
- 수정 회차에서도 디자인 단계(`design_requested`)를 다시 거칠지: 이번에는 거치지 않는다.
- 수정 구현에 스크린샷 넘기기: 워커용 첨부 내려받기 엔드포인트가 생기면 수정 회차 claim에 재검증 스크린샷을 붙인다(원격 워커 포함).

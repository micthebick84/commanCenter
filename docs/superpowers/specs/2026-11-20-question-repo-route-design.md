## 1. 목적

지금 질문을 하려면 먼저 레포(별칭)와 브랜치를 골라야 한다. 카탈로그는 16개이고 대부분 버전 형제(Netis 6.1~7.0)와 사이트 대시보드라, 어느 것을 골라야 하는지 아는 사람만 바로 질문할 수 있다. DB 접속도 메뉴를 열어 직접 골라야 하고(공용 접속이 있는 레포는 2개뿐), 그 레포에 접속이 있는지조차 메뉴를 열기 전에는 모른다.

이 기능은 **질문부터 쓰게 하고**, 보내는 순간 TypeSafe Jev가 질문이 가리키는 레포를 카탈로그에서 찾아 **대화 화면의 카드로 한 번 확인받은 뒤** 세션을 시작한다. 같은 카드에서 그 레포의 DB 접속을 붙일지도 제안한다.

## 2. 목표 · 비목표 · 반목표

**목표**
- 새 질문 화면에서 레포·브랜치를 고르지 않고 질문을 보낼 수 있다.
- 보낸 질문 아래에 추천 카드가 뜬다. 사이트·버전을 말한 질문은 추천 레포가 강조되어 버튼 한 번으로 시작한다.
- 못 좁히는 질문은 최근 쓴 레포와 비슷한 후보, 검색으로 고르게 한다.
- 카탈로그에 없는 레포면 요청 게시판(사이트 추가)으로 안내한다.
- 레포가 정해지면 같은 카드에서 DB 접속을 제안한다(있으면 연결, 없으면 등록 안내).
- 추천과 실제 선택을 기록해 나중에 자동 시작 기준을 정할 근거를 모은다.
- Jev가 꺼져 있거나 실패해도 같은 카드가 추천 표시 없이 동작한다.
- 레포를 아는 사람은 지금처럼 직접 고르고 카드 없이 바로 시작할 수 있다.

**비목표 (이번 범위 밖)**
- 레포 없는 세션, 레포 확정 전의 여러 턴 대화(사용자 결정 2026-11-20: 카드 한 번이면 충분).
- 자동 확정. 확률이 아무리 높아도 한 번은 확인받는다.
- 세션을 만든 뒤 대상 레포 바꾸기(작업 폴더와 Claude 세션 이어가기가 레포에 묶여 있다).
- 대화 중 제안(2단계, §10).
- 카드에서 참조 repo·MCP 도구 고르기. 지금 있는 자리(직접 고르기 모드의 칩 줄, 입력창 도구 메뉴, 대화 화면의 `참조 변경`)를 그대로 쓴다.
- 작업 등록 창의 레포 추천.
- 카드가 떠 있는 동안 새로고침해도 초안이 남는 것.

**반목표 (이렇게 되면 기능은 돌아가도 실패)**
- 사용자가 확인하지 않은 레포로 세션이 시작되는 것.
- 질문 전문·첨부 내용·DB 접속정보·카탈로그의 내부 설명(담당자 이름 등)이 외부 API로 나가는 것.
- Jev 장애나 키 없음 때문에 질문을 시작하지 못하는 것.
- 직접 고르던 사용자의 단계가 늘어나는 것.
- 추천 호출이 실패했을 때 질문 본문이 로그·오류 메시지에 남는 것.

## 3. 제약 (코드에서 확인한 것)

- 질문 세션은 레포가 세 곳에서 필수다: 화면 `canSubmit`(`pages/questions/index.vue`), `QuestionCreateRequest.repoCatalogId @NotNull`, DB `interview_session.github_repo NOT NULL`.
- `work_dir`는 첫 claim 때 레포 체크아웃 경로로 고정되고 Claude 세션 이어가기는 그 폴더에 묶인다. 첫 턴 프롬프트에도 레포 이름이 들어간다. → 레포는 **세션을 만들기 전에** 정해야 한다.
- 대화 스트림 안에서 사용자가 누르는 카드는 지금 없다(`AskUserQuestion` 금지, 진행 중 턴으로 가는 통로 없음). → 카드는 세션 이전의 **화면 상태**로 만든다.
- DB 접속은 레포에 묶여 있다(`db_connection.repo_catalog_id NOT NULL`, `validateSelection`이 레포 일치를 검사). → DB 제안은 레포가 정해진 뒤에만 가능하다.
- 새 질문은 지금도 레포를 고르면 공용(REPO) 접속을 최대 3개 미리 선택한다(`seedDefaults`).
- 카탈로그에서 레포를 설명하는 칸은 `alias`와 `description`뿐이다. `description`에는 담당자 이름이 들어 있는 행이 있다(예: "(개발자: …, 기술팀: …)").
- 질문 등록 API는 브랜치가 비면 조용히 `main`으로 채운다(카탈로그 기본 브랜치가 아니다).
- Jev: `POST https://api.typesafe.ai/v1/systemone`, `Authorization: Bearer`, Java SDK 없음. Choice 선택지 255개까지, 기본 64k 토큰. 문서에 한국어 지원 언급이 없다. 문서 권고: "해당 없음" 선택지 대신 짝 Noul, 첫 선택지 쏠림이 있으니 순서를 섞어 확인, 임계값은 자기 데이터로 정하기, 별칭(`jev-latest`)은 릴리스 때 움직이므로 임계값을 쓰면 버전 고정.
- 남아 있는 질문 세션은 14건(카탈로그 연결 6건)이라 과거 데이터로 정확도를 잴 수 없다.

## 5. 동작

### 5.1 새 질문 화면

입력창 위 선택 줄을 두 모드로 바꾼다.

- **자동(기본)**: 선택 줄 자리에 한 줄 표시 `레포: 질문을 보면 찾아 드려요 · 직접 고르기`. 레포·브랜치 선택 상자와 참조 칩 줄은 숨긴다. 보내기 조건은 질문 본문만이다.
- **직접 고르기**: 지금 화면 그대로(레포·브랜치 선택, 참조 칩 줄, DB 버튼). 보내면 카드 없이 바로 세션을 만든다. `자동으로 찾기`로 되돌아갈 수 있다.

마지막으로 쓴 모드는 브라우저에 기억한다(만드는 사람이 방식 결정).

### 5.2 자동 모드에서 보내기

1. 화면이 대화 모양으로 바뀐다: 내 질문 말풍선(첨부 칩 포함) + `✎ 질문 고치기` + AI 쪽 카드 자리(불러오는 중).
2. `POST /api/questions/route`를 부른다(§6.1).
3. 응답 상태에 따라 카드를 그린다(§5.3).
4. 사용자가 레포를 확정하면 기존 `POST /api/questions`(첨부가 있으면 multipart)를 부르고 `/questions/{id}`로 이동한다. 바디에는 고른 레포, **브랜치 조회로 받은 기본 브랜치(또는 카드에서 바꾼 브랜치, §5.3)**, 질문, 모델·effort, MCP, 카드에서 고른 `dbConnectionIds`, `routeId`가 들어간다.
5. `✎ 질문 고치기`를 누르면 입력창으로 돌아가고 카드는 사라진다(본문·첨부·모델 선택은 유지).

카드가 떠 있는 동안 입력창은 잠그고 `레포를 확정하면 답변이 시작됩니다`를 보여 준다.

### 5.3 카드 상태

| 상태 | 조건(§6.2) | 카드 |
|---|---|---|
| 추천 있음 | `CONFIDENT` | 제목 `이 레포에 대한 질문이 맞나요?`. 추천 레포를 강조(별칭, 설명, `추천` 표시, 브랜치). `다른 후보` 칩 최대 2개 + `🔍 다른 레포`. 버튼 `이 레포로 질문 시작` |
| 못 좁힘 | `AMBIGUOUS` | 제목 `어느 버전·사이트에 대한 질문인가요?`. `최근 사용` 칩(최대 3) + `비슷한 후보` 칩(최대 3, 최근 사용과 겹치면 뺌) + `🔍 전체 N개에서 찾기`. 고르기 전에는 버튼 비활성 `레포를 골라 주세요` |
| 카탈로그에 없음 | `NO_MATCH` | 제목 `등록된 레포 중에 맞는 곳을 찾지 못했어요`. 검색 + `사이트 추가 요청 →`(요청 게시판, 새 탭 — 질문 초안이 사라지지 않게) |
| 추천 꺼짐·실패 | `UNAVAILABLE` | `못 좁힘`과 같은 모양이되 `비슷한 후보` 줄이 없다. 실패 안내 문구는 띄우지 않는다 |

- 칩이나 검색에서 레포를 고르면 그 레포가 강조 자리로 올라오고 버튼이 켜진다. `추천` 표시는 Jev가 고른 레포에만 붙는다.
- 검색은 별칭·설명에 대한 화면 쪽 부분 일치다(목록은 이미 `GET /api/repo-catalog`로 받는다). 카드에는 **별칭과 설명**을 보여 준다.
- 브랜치: 카드에서 레포가 정해질 때마다 직접 고르기 모드와 같은 조회(`GET /api/repos/branches?catalogId=`)를 부른다(만든 사람 결정 — 카탈로그 기본 브랜치는 비어 있을 수 있고, 등록 API는 빈 브랜치를 `main`으로 채운다). 받은 기본 브랜치를 보여 주고, 누르면 지금의 브랜치 검색 선택이 열린다. 조회 중에는 시작 버튼을 잠그고, 실패하면 직접 고르기 모드와 같은 오류 문구를 카드에 보여 주며 시작을 막는다(다른 레포는 고를 수 있다).
- 등록이 거부되는 레포(지원하지 않는 호스트)는 Jev 후보·카드 칩·카드 검색에 넣지 않는다. 직접 고르기 모드의 선택 상자는 지금처럼 그 행을 보여 주고 고르면 오류를 낸다(바꾸지 않는다). 지원 여부는 저장된 `host` 칸이 아니라 등록과 같은 방식(`git_url`을 다시 해석 — `RepoCatalogService`)으로 판정해, 추천한 레포가 등록에서 거부되는 일이 없게 한다.

### 5.4 DB 줄

카드에서 레포가 정해질 때마다 그 레포의 접속 목록을 지금 쓰는 방식(`fetchDbConnections(repoId)`)으로 받아 레포 아래에 그린다. DB 기능이 꺼져 있으면(암호화 키 없음) 줄 자체가 없다.

| 접속 | 응답 `dbNeeded` | 모습 |
|---|---|---|
| 있음 | `true` | 접속마다 체크 상자, **미리 체크**(공용 먼저, 최대 3개). 문구 `DB 조회가 필요한 질문으로 보여 미리 골랐어요` |
| 있음 | `false` | 체크 상자, 체크 안 함 |
| 있음 | `null`(추천 꺼짐·실패) | 지금 규칙대로 공용 접속만 미리 체크 |
| 없음 | `true` | `이 레포에 연결할 DB 접속이 없습니다` + `내 DB 접속 추가`(지금의 개인 접속 등록 창을 그 레포로 연다. 등록하면 목록을 다시 받아 체크된 채로 보인다) |
| 없음 | `false`·`null` | 줄을 숨긴다 |

지금과 달라지는 점: 자동 모드에서 `dbNeeded=false`이면 공용 접속도 미리 체크하지 않는다(필요할 때만 붙인다). 직접 고르기 모드는 지금 그대로다.

## 6. API

### 6.1 `POST /api/questions/route`

인증 사용자 누구나. 바디 `{ "question": string }`(검증: 비어 있지 않음, 최대 20000자 — 등록과 같은 한도).

응답:

```json
{
  "routeId": 123,
  "state": "CONFIDENT | AMBIGUOUS | NO_MATCH | UNAVAILABLE",
  "recommendedRepoCatalogId": 11,
  "candidates": [ { "repoCatalogId": 11, "probability": 0.91 }, { "repoCatalogId": 3, "probability": 0.05 } ],
  "recentRepoCatalogIds": [8, 14, 3],
  "eligibleRepoCatalogIds": [3, 4, 5, 6, 7, 8],
  "dbNeeded": true
}
```

- `eligibleRepoCatalogIds`는 켜져 있고 등록 가능한 카탈로그 행 전체다(§5.3의 판정). 모든 상태(`UNAVAILABLE` 포함)에서 내려 주고, 카드의 칩·검색은 이 안에서만 고르게 한다. `candidates`·`recentRepoCatalogIds`·`recommendedRepoCatalogId`도 이 안의 값만 담는다.

- `recommendedRepoCatalogId`는 `CONFIDENT`일 때만 값이 있다.
- `candidates`는 확률 내림차순 상위 5개. `UNAVAILABLE`이면 빈 목록.
- `recentRepoCatalogIds`는 그 사용자의 질문 세션에서 최근에 쓴 순서로 서로 다른 레포 최대 3개(지금 켜져 있는 카탈로그 행만).
- `dbNeeded`는 `UNAVAILABLE`이면 `null`.
- 화면은 별칭·설명을 이미 받은 카탈로그 목록에서 찾고, 브랜치는 레포를 고를 때 따로 조회한다(§5.3).
- 추천 쪽 문제로는 **실패하지 않는다**: Jev 키 없음·기능 꺼짐·시간 초과·오류·응답 해석 실패는 모두 200 + `UNAVAILABLE`이다. 등록 가능한 카탈로그가 0개여도 `UNAVAILABLE`. 바디 검증 오류(빈 질문·길이 초과)와 인증 오류만 4xx다.
- 화면은 이 호출이 네트워크 오류·5xx로 끝나도 `UNAVAILABLE` 카드를 그린다(후보는 카탈로그 목록 전체, 등록 불가 행을 고르면 직접 고르기 모드와 같은 오류).

### 6.2 판정

Jev에 **한 번의 요청으로** 아래 질문을 함께 묻는다(서로의 답을 보지 못하는 독립 질문).

상태(state)로 보내는 것:
- `question`: 질문 본문에서 공백을 한 칸으로 줄이고 **앞 500자**만 자른 것.
- `repositories`: 켜져 있고 등록 가능한 카탈로그 행(§5.3의 판정)마다 `{ key: "r{id}", name: 별칭, hint: 추천 키워드 }`. **`description`은 보내지 않는다**(§7).

질문:

| id | 종류 | 묻는 것 |
|---|---|---|
| `repo` | Choice | 질문이 어느 저장소에 대한 것인가. 선택지 = `r{id}`마다 `별칭 — 추천 키워드`. "해당 없음" 선택지는 두지 않는다 |
| `mentions_target` | Noul | 질문이 특정 사이트·고객·제품·버전을 이름으로 가리키는가 |
| `target_listed` | Noul | 질문이 가리키는 사이트·제품·버전이 `repositories` 안에 있는가 |
| `needs_db` | Noul | 답하려면 소스 코드만이 아니라 실제 데이터베이스의 테이블 구조나 데이터를 조회해야 하는가 |

지시문·기준은 영어로 쓰고(상태의 한국어는 그대로), 정확한 문구는 만드는 사람이 TypeSafe 현재 문서(Choice·Noul·companion-noul·confidence)를 읽고 정한다.

코드가 정하는 것:
- 첫 선택지 쏠림을 줄이려고 **요청마다 선택지 순서를 섞는다**.
- `CONFIDENT`: `mentions_target ≥ 0.7` 그리고 `target_listed ≥ 0.7` 그리고 `repo` 1위 확률 ≥ 0.5.
- `NO_MATCH`: `mentions_target ≥ 0.7` 그리고 `target_listed ≤ 0.3`.
- 그 밖은 `AMBIGUOUS`.
- `dbNeeded`: `needs_db ≥ 0.6`.
- 네 임계값은 설정값이다(§8). 위 숫자는 시작값이고, 항상 확인받으므로 틀려도 카드의 첫 모습만 달라진다. 기록(§6.4)이 쌓이면 다시 정한다.

호출: 모델은 **버전 고정**(`jev-1.14.0`, 설정값). 전체 상한 3초, 429·529는 상한 안에서 한 번만 다시 시도. 실패하면 `UNAVAILABLE`. 로그에는 상태·소요 시간·HTTP 코드만 남기고 **질문 본문과 키는 남기지 않는다**.

### 6.3 `POST /api/questions` (기존)

`QuestionCreateRequest`에 선택 칸 `routeId`(Long, null 가능)를 더한다. 값이 있으면 세션을 만든 같은 트랜잭션에서 그 추천 기록에 고른 레포와 세션 id를 적는다. 기록이 없거나 남의 것이면 **조용히 무시한다** — `routeId` 때문에 질문 등록이 실패하면 안 된다. 그 밖의 검증·동작은 지금과 같다.

### 6.4 추천 기록 `com.question_route_log` (V47 — 병합 직전 main 최대 번호 확인)

| 칸 | 내용 |
|---|---|
| `id`, `created_at`, `user_id` | |
| `question_excerpt` | Jev에 보낸 500자(보낸 것만 남긴다). `UNAVAILABLE`이어도 남긴다 |
| `state`, `model` | 판정 상태, 응답한 모델 버전(`UNAVAILABLE`이면 null) |
| `candidates` | JSONB — 상위 5개 `{repoCatalogId, probability}` |
| `mentions_target`, `target_listed`, `needs_db` | Noul 값(null 가능) |
| `recommended_repo_catalog_id` | null 가능 |
| `chosen_repo_catalog_id`, `session_id`, `chosen_at` | 등록 때 채움. 끝까지 비어 있으면 카드에서 그만둔 것 |
| `latency_ms` | |

카탈로그·세션을 가리키는 칸은 FK를 걸되 지워지면 NULL(`ON DELETE SET NULL`). 보존 기간은 두지 않는다(행이 작다). 조회 화면은 만들지 않는다 — 임계값을 다시 정할 때 SQL로 본다.

## 7. 카탈로그: 추천 키워드 칸

`com.repo_catalog`에 `route_hint TEXT`(null 가능, 같은 V47)를 더한다. 관리 화면(`pages/admin/repo-catalog.vue`) 폼에 `추천 키워드` 입력 칸을 두고 안내 문구를 단다: `질문에서 이 레포를 찾을 때 쓰는 말(고객사·사이트 별칭, 버전, 주요 화면). 외부 추천 서비스로 전송되니 사람 이름·접속정보는 적지 마세요.` 최대 500자.

- Jev에는 **별칭과 추천 키워드만** 보낸다. 키워드가 비어 있으면 별칭만 보낸다.
- 기존 `description`은 카드에 보여 주는 용도로만 쓰고 밖으로 보내지 않는다.
- `GET /api/repo-catalog`(일반 사용자)는 `route_hint`를 내려 주지 않는다. 지금은 일반·관리자 조회가 같은 `RepoCatalogDto.View`를 쓰므로, 일반 조회에서 이 칸을 비우거나 응답 형을 나눈다(방식은 만드는 사람 결정).
- 관리 화면의 켜기/끄기 토글은 일부 칸만 담은 바디를 보낸다. 수정 API에서 `routeHint`가 null이면 **유지**, 빈 문자열이면 비움으로 처리해 토글이 키워드를 지우지 않게 한다.
- 16개 행의 키워드 채우기는 관리자 몫이다. 비어 있어도 별칭에 사이트·버전이 들어 있어 기본 동작은 한다.

> 이 칸은 대화에서 정한 "새 칸 없이 설명 칸을 쓴다"를 뒤집는다. 설명 칸에 담당자 이름이 들어 있어 그대로 밖으로 보낼 수 없기 때문이다. **사용자 확인 필요.**

## 9. 시험 · 배포

**시험**
- Java: 판정 로직(임계값 조합 → 상태), Jev 클라이언트(목 HTTP — 정상·시간 초과·429·깨진 응답 → `UNAVAILABLE`), 500자 자르기, `route` 컨트롤러, `routeId` 연결(남의 기록·없는 기록 무시), 최근 레포 조회.
- 프론트: 카드 네 상태, 칩으로 레포 바꾸기, DB 줄 다섯 경우, `질문 고치기`, 직접 고르기 모드가 지금과 같은 바디를 보내는지, 폰 폭(390px).
- `frontend/scripts/hydration-smoke.mjs`에 새 API 목을 넣는다.
- **한국어 정확도 확인(구현 첫 단계)**: 실제 카탈로그 별칭과 지어낸 질문 30개 안팎(사이트를 말한 것·버전만 말한 것·아무것도 말하지 않은 것·없는 사이트를 말한 것·DB가 필요한 것)을 스크립트로 Jev에 보내 상태 판정을 본다. 사이트·버전을 말한 질문의 1위 적중이 눈에 띄게 낮으면(만드는 사람 판단, 기준 80%) 구현을 멈추고 사용자에게 알린다. 실제 사용자 질문은 쓰지 않는다.
  - 키: 이 확인은 배포 전에 돌므로 `public.env`가 아니라 스택이 읽지 않는 별도 파일 `%USERPROFILE%\netis-maker\typesafe.env`(`TYPESAFE_API_KEY=…` 한 줄)에서 읽는다. **사용자가 구현 시작 전에 이 파일을 만들어 둔다.** 스크립트는 키를 출력하지 않는다.
  - 사이트·버전을 말하지 않은 질문에서 `repo` 확률이 어떻게 퍼지는지도 적어 둔다. 형제 버전 사이에 고르게 퍼지면 `비슷한 후보` 칩이 뜻 없는 추천이 되므로, 그 줄에 확률 하한을 둘지(없으면 줄을 숨길지) 이 결과로 정한다.
  - 추천 키워드: 두 번 잰다 — 별칭만 보냈을 때와, 스크립트에 적은 초안 키워드를 함께 보냈을 때. 기준(80%)은 초안 키워드를 보낸 쪽에 적용하고, 그 초안은 관리 화면에 넣을 값으로 사용자에게 건넨다.

**배포 순서**
1. 인터뷰 서비스·이 PC 워커(비밀 제거 목록) 재기동.
2. API(V47).
3. 프론트(`.output` 재빌드).
4. `public.env`에 `TYPESAFE_API_KEY`를 넣고 API 재기동(사용자 몫: 키 입력). 키를 넣기 전에도 1~3은 `UNAVAILABLE` 카드로 동작한다.
5. 관리 화면에서 추천 키워드 채우기(사용자 몫).

원격 워커 2대는 `public.env`를 쓰지 않아 jar를 바꾸지 않아도 된다.

## 10. 2단계 윤곽 (이번 계획에 넣지 않음)

대화 화면에서 추가 질문을 **보내기 전에** 같은 판정을 부른다(상태에 대상·참조 레포를 더해).
- 다른 카탈로그 레포를 가리키면: `참조로 추가하고 보내기` / `그대로 보내기` / `그 레포로 새 질문`.
- DB가 필요해 보이는데 연결이 없으면: `DB 연결하고 보내기` / `그대로 보내기`.
- 제안이 없으면 지금처럼 바로 보낸다. 변경은 지금의 `ask` 바디(`refRepos`·`dbConnectionIds`)로 싣는다.

1단계 기록으로 임계값을 정한 뒤 따로 설계한다.

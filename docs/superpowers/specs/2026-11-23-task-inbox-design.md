# 처리함 — 여러 작업의 인터뷰·승인을 한 화면에서 처리 설계

- 날짜: 2026-11-23
- 상태: 사용자 검토 대기
- 범위: 프론트엔드(Nuxt)만. API·워커·인터뷰 서비스·DB 변경 없음
- 선행 스펙: `2026-09-06` 작업 탭 재설계(“확인 필요” 묶음 `attentionGroup`), `2026-10-24-task-ref-repos-design.md` §7.4(인터뷰 답변 때 참조 변경), `2026-11-03-interview-superpowers-toggle-design.md`(간단 인터뷰·계획 고쳐 달라기), `2026-11-03-deploy-e2e-reverify-design.md` §4(수정 요청), `2026-10-13-task-close-phase-design.md`·`2026-11-13-close-base-sync-design.md`(종료·기준 브랜치 반영)

## 1. 목적

인터뷰부터 구현 승인까지 여러 작업이 동시에 진행될 때(인터뷰 서비스는 동시 4건), 관리자는 지금 작업마다 상세 화면을 따로 열어 인터뷰에 답하고 승인한다. 에이전트가 다음 질문을 만드는 1~5분 동안 다른 작업을 처리하면 전체가 빨라지는데, 지금은 그 사이를 오가는 일이 번거로워 한꺼번에 처리하기 힘들다.

이 기능은 관리자에게 **처리함** 화면을 준다. 왼쪽에 확인이 필요한 작업이 모두 모이고, 오른쪽에서 고른 작업을 그 자리에서 처리하며, 하나를 처리하면 다음 대기 건으로 넘어간다.

## 2. 목표 · 비목표 · 반목표

**목표**
- 관리자 “확인 필요”(`attentionGroup(task, true) === 'attention'`) 13개 상태를 **모두** 처리함 안에서 처리한다 — 인터뷰 답변, 계획 확정, 인터뷰 시작 승인, 디자인 검토, 수정 요청 승인·반려, 종료 승인·반려, 실패 처리(재시도·구현 재시도·재배포·종료 재시도 등).
- 처리에 성공하면 다음 대기 건으로 자동으로 넘어간다.
- 에이전트가 새 질문을 올리면 5초 안에 목록에 다시 나타난다.
- 작업을 오가도 쓰던 인터뷰 답변이 남는다(처리함을 떠나기 전까지).
- 폰에서도 쓸 수 있다(목록 → 전체 화면 처리 → 다음 건).

**비목표 (이번 범위 밖)**
- 일괄 승인(여러 건을 체크해 한 번에). 사용자 결정 2026-11-23 — 대신 순차 처리를 빠르게 한다.
- 서버 변경(새 API·필터·정렬 고정). 목록은 기존 `GET /api/tasks`를 쓴다.
- 소리·데스크톱 알림·푸시.
- 관리자끼리 작업 나눠 맡기·잠금. 두 관리자가 같은 건을 누르면 서버의 409를 그대로 알린다.
- 요청 게시판의 처리 대기(요청 탭 배지)는 넣지 않는다.
- 일반 사용자용 처리함. 관리자 전용이다.
- 일반 사용자 “작업” 배지의 50건 상한 문제(§11 후속).

**반목표 (이렇게 되면 기능은 돌아가도 실패)**
- 관리자가 누르지 않았는데 무언가가 제출되는 것. 자동 이동은 **화면만** 바꾸고 아무것도 보내지 않는다.
- 폴링·건 전환 때문에 쓰던 답변이 사라지는 것.
- 확인이 필요한 작업이 처리함에서 **조용히** 빠지는 것. 못 읽은 건이 있을 수 있으면 화면에 알린다(§6.1).
- 작업 상세 화면의 동작이 바뀌는 것. 공용으로 빼는 코드는 상세 화면의 기존 시험이 그대로 통과해야 한다.
- 대화 패널(SSE)을 여러 개 동시에 여는 것. 한 번에 하나만 연다.

## 3. 접근 방식

**화면 형태**

| | A. 처리함(목록 + 처리 영역) | B. 패널 타일 | C. 일괄 승인 |
|---|---|---|---|
| 내용 | 왼쪽 대기 목록, 오른쪽 고른 건 처리, 처리하면 다음 건 | 2~4개 대화 패널을 나란히 | 승인대기 여러 건을 체크해 공통 설정으로 한 번에 |
| 장점 | 한 번에 한 건에 집중, SSE 1개, 폰도 가능 | 여러 대화를 동시에 봄 | 승인 클릭 수가 가장 적음 |
| 단점 | 동시에 두 건을 보지는 못함 | 넓은 화면만, SSE가 패널 수만큼 | 건마다 다른 값(타입·DB·참조)을 못 봄, 종료·디자인은 위험 |

**A를 택했다**(사용자 결정 2026-11-23, 처리 범위 = 확인 필요 전부, C는 넣지 않음).

**처리 영역을 만드는 방법**

| | ① 처리함 전용 처리 영역 | ② 상세 화면 통째로 넣기 |
|---|---|---|
| 내용 | 상태별로 필요한 부분만 보인다. 상세의 동작 함수는 공용 모듈로 빼서 함께 쓴다 | 1,778줄 상세 페이지를 컴포넌트로 바꿔 오른쪽에 넣는다 |
| 장점 | 처리에 집중돼 빠르다. 기존 부품(대화 패널·디자인 카드·재시도 창·재배포 창)을 그대로 쓴다. 상세 화면 위험이 작다 | 기능이 늘 상세와 같다 |
| 단점 | 새 대기 상태가 생기면 처리함에도 더해야 한다(§8 시험이 빠진 것을 잡는다) | 큰 리팩터로 상세가 깨질 위험, 오른쪽이 길고 산만 |

**①을 택했다**(사용자 결정 2026-11-23). 상세 페이지를 iframe으로 띄우는 길도 봤지만 건마다 앱을 새로 띄워 느려 뺐다.

## 4. 확정된 결정

| 항목 | 결정 | 출처 |
|---|---|---|
| 처리 범위 | 관리자 확인 필요 13개 상태 전부, 처리함 안에서 | 사용자 |
| 일괄 승인 | 넣지 않음. 순차 처리 + 자동 다음 건 | 사용자 |
| 처리 영역 | 처리함 전용(①), 동작 함수는 상세와 공용 | 사용자 |
| 인터뷰 시작 승인 | 승인 창의 내용을 처리 영역에 펼쳐 보인다(창을 띄우지 않음) | 사용자(일괄 승인 질문의 추천안) |
| 주소 | `/inbox` (관리자 전용) | 설계자 제안 |
| 처리 순서 | 답변 대기 → 계획 확인 → 인터뷰 시작 승인 → 디자인 검토 → 수정 요청 승인 → 종료 승인 → 실패, 묶음 안은 오래 기다린 순 | 설계자 제안 |
| 다음 건 | 처리하지 않은 건 중 **맨 위**(우선순위가 가장 높은 건) | 설계자 제안 |
| 자동 이동 | 기본 켬, 끄기 토글(브라우저에 기억) | 설계자 제안 |
| 쓰던 답변 | 처리함 안에서 작업을 오가도 유지(메모리), 첨부 파일은 유지 안 함 | 설계자 제안 |
| 키보드 | `j` 다음 / `k` 이전 — 입력칸에 포커스가 있을 때는 동작 안 함 | 설계자 제안 |
| 들어가는 곳 | 데스크톱 위 탭 “처리함”+배지, 폰 관리자 하단 바 “처리함”+배지(작업 탭의 관리자 배지는 처리함으로 옮김) | 설계자 제안 |
| 서버 | 변경 없음. 목록은 `sort=updatedAt,desc&size=200` | 설계자 제안 |

## 5. 화면

### 5.1 들어가는 곳 · 권한

- 주소 `/inbox`, 새 페이지 `frontend/pages/inbox.vue`(레이아웃 `default`).
- 관리자 전용. 전역 미들웨어(`middleware/auth.global.ts`)의 관리자 경로 검사에 `/inbox`를 더한다 — 관리자가 아니면 `/tasks`로 보낸다(`/admin*`과 같은 `redirectTo`).
- 데스크톱 위 탭(`layouts/default.vue`): 관리자에게 “작업” 다음에 `처리함` 탭(`/inbox`)과 건수 배지. 배지 색은 지금 폰의 작업 배지와 같은 `warning`.
- 폰 하단 바: 관리자는 `작업 · 처리함 · 질문 · 요청 · 관리` 5칸(아이콘 `inbox`). 관리자의 “확인 필요” 배지는 **작업 탭에서 처리함 탭으로 옮긴다**. 관리자가 아닌 사람의 하단 바·작업 배지는 지금 그대로다. 390px에서 5칸 글자가 잘리지 않는지 확인한다.
- 템플릿의 관리자 분기는 `useHydrationSafeAuth()`로 한다(CLAUDE.md SSR 하이드레이션 규칙).

### 5.2 목록 (데스크톱 왼쪽, 폰 전체)

- 묶음과 순서(§4). 묶음 머리에 이름과 건수. 빈 묶음은 그리지 않는다.

  | 묶음 | 상태 |
  |---|---|
  | 답변 대기 | `INTERVIEW_INPUT` |
  | 계획 확인 | `INTERVIEW_REVIEW`, `COMPLETED`(레거시 분석완료 — 지금은 진입점이 없지만 확인 필요 상태라 넣는다) |
  | 인터뷰 시작 승인 | `AWAITING_APPROVAL` |
  | 디자인 검토 | `DESIGN_REVIEW` |
  | 수정 요청 승인 | `FIX_REVIEW` |
  | 종료 승인 | `CLOSE_REVIEW` |
  | 실패 | `FAILED`, `DESIGN_FAILED`, `IMPLEMENTATION_FAILED`, `DEPLOY_FAILED`, `DEPLOY_LOST`, `CLOSE_FAILED` |

- 묶음 안은 `updatedAt` 오름차순(오래 기다린 건이 위). 상태가 바뀔 때 `updatedAt`이 갱신되므로 “그 상태로 기다린 시간”에 가깝다.
- 행: `#id 제목`(한 줄 말줄임), 레포 별칭, 상태 칩(`CHIP` 색), 타입 칩(있을 때), 대기 시간(`ageOf(updatedAt)`). 고른 행은 강조.
- 처리한 건은 목록 폴링이 따라오기 전에도 바로 숨긴다(§5.4).
- 빈 상태: “확인할 작업이 없습니다” + 작업 목록 링크.
- 맨 위 한 줄: 전체 건수와 `처리 후 다음 건으로` 토글(§5.4).
- 200건 안내: 목록 응답의 `totalElements`가 받은 건수보다 크면 목록 위에 “최근 변경된 200건만 봤습니다 — 오래된 작업은 작업 목록에서 확인하세요”를 띄운다(조용히 빠지지 않게).

### 5.3 처리 영역 (데스크톱 오른쪽, 폰 전체 화면 창)

**머리글(모든 상태 공통)**
- `#id 제목`, 상태 칩, 레포 별칭·브랜치, 타입 칩, 요청자, 대기 시간.
- `이전` / `다음` 버튼(목록 순서), `상세 열기 ↗`(새 탭 `/tasks/{id}` — 처리함 흐름을 끊지 않게).
- 접혀 있는 `등록 설명·첨부`: 설명은 상세와 같이 `<pre style="white-space: pre-wrap">`, 첨부는 상세와 같은 내려받기 칩. 인터뷰 질문에 답할 때 원래 요청을 다시 볼 일이 많아서다.
- “다음 할 일” 한 줄: `nextAction(task, true).text`.
- 실패 상태와 `failureReason`이 있으면 실패 사유(긴 글은 `.md-scroll`).

**상태별 본문** — 처리 버튼은 작업 상세가 관리자에게 그 상태에서 보여 주는 것과 같은 집합이다(구현자는 `pages/tasks/[id].vue`와 대조한다). 확인창·문구는 상세와 같은 것을 쓴다(공용 모듈, §7.1).

| 상태 | 본문 | 처리 | 다음 건으로 넘어가는 때 |
|---|---|---|---|
| 입력대기 | 참조 줄(`RefRepoChips` + `TaskRefChangeMenu` “✎ 참조 변경”) + `InterviewPanel` | 답변 보내기 | 답변 전송 성공(`answered`, §7.4) |
| 플랜승인대기 | 참조 줄 + `InterviewPanel`(계획·확정 화면 — 구현 방식·디자인·목업·참조 확정이 패널 안에 있다) | 구현 진행 · (간단 인터뷰) 계획 고쳐 달라기 · 인터뷰 취소 | `confirmed` / `answered`. 인터뷰 취소(`close`)는 작업이 승인대기로 돌아가 여전히 확인 필요이므로 **넘어가지 않고** 다시 읽는다 |
| 분석완료(레거시) | 다음 할 일 한 줄 | 구현 승인 | 성공 |
| 승인대기 | 승인 폼(`ApproveForm`, §7.3 — 요약·타입·지난 인터뷰·모델·추론·superpowers·MCP·DB·참조·사용량, 미리 채움) | 승인하고 인터뷰 시작 · 작업 취소 | 승인 성공 / 취소 성공 |
| 디자인 검토 | `DesignReviewCard` | 승인 · 반려(피드백) | 카드의 `refresh`(승인·반려 성공 때만 나온다) |
| 수정승인대기 | `FixRequestHistory`(대기 중인 요청 본문) + 배포 주소 링크 | 수정 승인(방식 고름) · 반려(사유) | 성공 |
| 종료승인대기 | PR/MR 링크, 배포 주소, 종료 단계 목록 | 종료 승인(확인창 — 승인 대기 SQL 경고 포함) · 반려(사유) | 성공 |
| 실패·디자인실패 | 실패 사유 | 재시도 | 성공 |
| 구현실패 | 실패 사유, PR/MR·브랜치 링크 | 구현 재시도(`ImplementationRetryDialog`, 회차 정보 포함) · 회차면 수정 중단/반영 중단 | 재시도 창 `submitted` / 중단 성공 |
| 배포실패 | 실패 사유(배포 로그는 `상세 열기`) | 재배포(`DeployEnvDialog`) · 수정 요청(`FixRequestDialog`, 가능할 때) | 창 `submitted` |
| 배포중단됨 | 실패 사유, 배포 주소 | 재배포 · 종료 요청 · 수정 요청(가능할 때) | 성공·창 `submitted` |
| 종료실패 | 실패 사유, 종료 단계 목록 | 종료 재시도 · 기준 브랜치 반영(가능할 때) · 종료 취소(병합 전) · 산출물 없이 마무리 · 패치 없이 마무리(가능할 때) | 성공 |

**처리할 것이 없는 상태**(고른 건이 다른 곳에서 처리됐거나 처리 뒤 자동 이동을 껐을 때)
- `INTERVIEWING`(인터뷰중): 대화 패널을 계속 보인다 — 에이전트가 답을 만드는 과정을 볼 수 있게. 위에 “에이전트가 답을 만드는 중입니다” 한 줄.
- 그 밖: “지금 처리할 것이 없습니다(현재: {statusLabel})” + 다음 할 일 한 줄 + `상세 열기` + `다음 건` 버튼.

**처리함에 두지 않는 것**(상세 화면에만): 진행 이력, 앱 로그·빌드 로그, 분석 결과 마크다운, 사용량 칩, DB 변경 카드, 산출물·패치 내려받기, 메일 다시 보내기. 필요하면 `상세 열기`.

### 5.4 다음 건으로 넘어가기

- **넘어가는 계기는 관리자가 처리함에서 누른 동작의 성공뿐이다**(§5.3 표의 마지막 칸). 폴링·SSE로 본 상태 변화로는 넘어가지 않는다 — 읽던 화면이 갑자기 바뀌지 않게.
- 다음 건 = 처리한 건을 뺀 목록의 **맨 위**. 남은 건이 없으면 빈 상태(폰은 창을 닫고 “모두 처리했습니다” 알림).
- 처리한 건 숨기기: 동작이 성공하면 그 작업의 `(id, 그때 목록의 status, 그때 목록의 updatedAt)`을 기억하고, 목록 행이 같은 `status`·`updatedAt`인 동안은 숨긴다. 서버가 상태를 바꾸면 `updatedAt`이 바뀌므로 기록을 지운다. 이렇게 해야 에이전트가 빨리 다음 질문을 올려 폴링 사이에 `입력대기 → 인터뷰중 → 입력대기`가 지나가도(행의 `updatedAt`이 달라졌으므로) 다시 보인다.
- `처리 후 다음 건으로` 토글(기본 켬, `localStorage` `netis-maker-inbox-auto-next`, 읽기·쓰기는 try/catch). 끄면 처리한 건에 그대로 머문다(인터뷰면 에이전트가 답하는 과정이 보인다).
- 다른 곳(상세 화면·다른 관리자·폰)에서 처리돼 고른 건이 확인 필요에서 빠지면 넘어가지 않고 §5.3의 “처리할 것이 없는 상태”를 보인다.

### 5.5 건 전환 · 키보드 · 쓰던 답변

- 고른 작업은 주소 쿼리 `?task={id}`에 둔다(새로 고침·뒤로 가기·링크). 들어왔을 때 쿼리가 없거나 그 작업이 목록에 없으면 맨 위 건을 고른다(쿼리의 작업이 확인 필요에서 빠진 경우에는 §5.3 “처리할 것이 없는 상태”로 그 작업을 보인다).
- `j` 다음 / `k` 이전(목록 순서). 포커스가 `input`·`textarea`·`[contenteditable]` 안이면 무시한다. 다이얼로그가 열려 있어도 무시한다.
- 쓰던 답변: 처리함이 세션 id별 답변 글을 메모리에 들고 대화 패널과 양방향으로 묶는다(§7.4 `draft`). 다른 건을 갔다 돌아오면 남아 있고, 처리함을 떠나면 사라진다. 고른 첨부 파일은 전환 때 사라진다(안내 없음 — 승인 폼의 선택값도 전환 때 기본값으로 돌아간다).

### 5.6 폰 (`$q.screen.lt.md`)

- 목록만 전체 폭으로 보인다. 행을 누르면 `maximized` 다이얼로그(내용 루트는 `<div>` — CLAUDE.md `q-dialog` 규칙)로 처리 영역을 연다: 위 바에 닫기·제목·이전/다음, 아래는 처리 영역. 대화 패널은 상세의 대화 시트처럼 `fill`로 남은 높이를 쓴다.
- 자동 이동은 창 안의 내용만 바꾼다. 처리할 건이 없으면 창을 닫는다.
- 다이얼로그 안의 확인창·재시도 창은 기존 부품 그대로(폰 전체 화면 규칙 `useFullscreenDialog` 포함).

## 6. 데이터

### 6.1 목록

- `GET /api/tasks?mine=false&size=200&sort=updatedAt,desc`를 5초마다(`useTaskPolling`). 응답의 `content` 중 `attentionGroup(t, true) === 'attention'`만 쓴다. 정렬을 거는 이유는 지금 목록 쿼리(`TaskRepository.findAllActive`)에 순서가 없어, 작업이 많아지면 200건 안에 어떤 작업이 들지 정해지지 않기 때문이다(최근 변경 순이면 오래 묵은 확인 필요 건만 빠질 수 있고, 그때는 §5.2 안내가 뜬다).
- 이 정렬은 서버 변경 없이 Spring Data `Pageable` 정렬로 된다(JPQL `@Query`에 정렬이 붙는다, 엔티티 필드 `Task.updatedAt`, 기본 최대 페이지 2000). **구현 첫 단계에서 라이브 API에 한 번 호출해 순서를 확인한다** — 안 되면 멈추고 사용자에게 알린다(서버 변경이 필요해지면 배포 순서가 바뀐다).
- 목록 응답(`TaskResponse.of(t, null)`)은 상세 응답보다 덜 채워진다 — `interviewSessionId`·`design`·`analysis`·첨부가 없고, 인터뷰 중 참조는 세션 값(`withRefRepos`)이 아니라 작업에 저장된 값이다. 목록은 왼쪽에만 쓴다.
- 이 조회와 확인 필요 거르기는 `composables/taskInbox.ts`의 함수 하나로 두고, 레이아웃의 관리자 배지(§6.3)도 같은 함수를 쓴다.

### 6.2 고른 작업

- `GET /api/tasks/{id}`를 5초마다(`useTaskPolling`, 작업 상세와 같은 방식). 처리 영역은 전부 이 응답으로 그린다. 고른 작업이 바뀌면 이전 폴링을 멈추고 새로 시작한다(한 번에 한 작업).
- 대화 패널은 세션 id를 `onMounted`에서만 읽으므로 `:key="interviewSessionId"`로 둔다 — 같은 세션의 폴링으로는 다시 붙지 않고, 다른 작업으로 바꾸면 SSE를 닫고 새로 연다. 승인 폼은 `:key="task.id"`(§7.3).
- 작업이 처리 뒤 상태를 바꿨을 때 대화 패널의 상태 알림(`status`)이 입력대기·계획 완료로 바뀌면 그 작업을 바로 다시 읽는다(상세의 `onInterviewStatus`와 같은 이유 — 참조 고정 상태가 폴링보다 늦게 온다).

### 6.3 배지

- 레이아웃의 관리자 배지 수 = §6.1 함수의 결과 건수(처리함과 같은 기준). 지금처럼 경로가 바뀔 때 다시 센다. 관리자는 데스크톱에서도 센다(위 탭 배지). 관리자가 아닌 사람은 지금 코드 그대로(`mine=true&size=50`, 폰에서만).
- 처리함 페이지 안에서는 목록 폴링으로 건수가 실시간이다(위 탭 배지는 경로가 바뀔 때만 갱신 — 같은 페이지에 머무는 동안 탭 배지와 목록 건수가 잠시 다를 수 있다).

## 7. 기존 코드 변경

### 7.1 작업 동작 공용 모듈 — `composables/useTaskActions.ts`

`pages/tasks/[id].vue`의 동작 함수를 옮긴다: `approve`(레거시 구현 승인)·`retry`·`cancelTask`·`closeAction`과 그 위의 `requestClose`·`approveClose`·`retryClose`·`cancelClose`·`syncBase`·`rejectClose`·`skipPatch`·`skipArtifact`·`approveFix`·`rejectFix`·`withdrawFix`·`abortFix`, 그리고 버튼 표시 판정(`canCancelClose`·`canSyncBaseNow`·`canSkipArtifactClose`·`canSkipPatchClose`·`canAbort`·`canFixRequest`·`canAdminRequestCloseLost`).
- 입력: 작업 `Ref`, 다시 읽기 함수. 판정 계산에 쓰는 `isAdmin`·`isOwner`는 지금처럼 스토어에서 읽는다.
- 각 동작은 **`Promise<boolean>`**(서버가 받아들였으면 true, 확인창 취소·실패면 false)을 돌려준다. `$q.dialog().onOk` 기반(`approveFix`·`rejectFix`·`rejectClose`)도 약속으로 감싼다. 상세는 반환값을 쓰지 않는다.
- 확인창 문구·알림 문구·중복 클릭 방지(`closeInFlight`)는 그대로.
- 받아들이는 기준: `test/task-detail-*.spec.ts` 전부가 **고치지 않고** 통과한다.
- 동작 분배(`onAction`)·배포 다이얼로그 열기·인터뷰 시트처럼 화면에 묶인 것은 상세에 남긴다.

### 7.2 인터뷰 참조 초안 공용 모듈 — `composables/useInterviewRefDraft.ts`

상세의 참조 초안(`pickedRefs`·`refsSeededFor`·`refsSyncedTo`·그 `watch`·`answerRefs`·`canChangeRefs`·`showRefRow`)을 옮겨 상세와 처리함이 같이 쓴다. 규칙(세션마다 시드, 보내지 않은 변경이 없을 때만 서버 집합을 따라감)은 그대로. 받아들이는 기준: `test/task-detail-refs.spec.ts`가 고치지 않고 통과한다.

### 7.3 승인 폼 분리 — `components/ApproveForm.vue`

`ApproveDialog.vue`의 내용(상태·불러오기·`approve`)을 `ApproveForm`으로 옮기고 `ApproveDialog`는 `q-dialog` 껍데기(폰 위 바·취소 버튼·`persistent`)로 남긴다.
- `ApproveForm`: props `task`, emits `approved`·`cancel`(취소 버튼을 보일지는 prop), `defineExpose({ approve })`. 불러오기(`init`)는 **마운트 때 한 번**이다 — 부모는 작업마다 `:key="task.id"`로 다시 마운트한다. 같은 작업의 폴링으로 `task` 객체가 바뀌어도 관리자가 고른 값을 되돌리지 않는다.
- `ApproveDialog`는 열 때마다 폼을 새로 마운트한다(지금의 “열 때마다 초기화”와 같은 동작). `v-model`·`task`·`approved`·`defineExpose({ approve })`·모든 `data-test` 이름은 그대로.
- 맨 아래 “다음 단계” 안내의 마지막 문장(“답변은 이 작업 화면의 대화형 분석 카드에서 합니다”)은 처리함에서는 “첫 질문이 오면 처리함의 답변 대기에 올라옵니다”로 바꾼다(prop).
- 받아들이는 기준: `components/ApproveDialog.spec.ts`·`test/task-detail-approve.spec.ts`가 고치지 않고 통과한다.

### 7.4 대화 패널 — `components/InterviewPanel.vue` (덧붙이기만)

- emit `answered`: 작업 인터뷰(`kind`가 QUESTION이 아님)의 답변·계획 고쳐 달라기 전송이 성공했을 때.
- `v-model:draft`(선택): 주어지면 입력창 글(`answer`)을 그 값과 묶는다. 주어지지 않으면 지금처럼 내부 상태.
- 상세·질문 화면은 둘 다 쓰지 않으므로 동작이 그대로다. 받아들이는 기준: `components/InterviewPanel.spec.ts`가 고치지 않고 통과한다.

### 7.5 처리함 순수 로직 — `composables/taskInbox.ts`

묶음 정의(§5.2), 목록 조회·거르기(§6.1), 묶음·정렬, 처리한 건 숨기기(§5.4), 다음 건 고르기, 키보드 무시 판정 같은 화면과 무관한 것은 여기 두고 단위 시험한다.

### 7.6 그 밖

- `middleware/auth.global.ts`: `/inbox` 관리자 검사.
- `layouts/default.vue`: 위 탭·하단 바·배지(§5.1, §6.3).
- `scripts/hydration-smoke.mjs`: 로그인 경로 목록에 `/inbox`, `/inbox?task=<목 작업 id>`. 목록 목(`/api/tasks`)에 확인 필요 상태 작업이 들어 있는지 확인하고 없으면 더한다. 정렬·크기 쿼리는 pathname만 비교하므로 같은 목이 답한다.

## 8. 시험

- `taskInbox.spec.ts`(순수): 묶음·순서·대기 시간 정렬, **확인 필요 상태 전부가 정확히 한 묶음에 들고 묶음의 상태는 전부 확인 필요인지**(`STAGES`의 모든 상태로 `attentionGroup(…, true)`를 돌려 대조 — 새 대기 상태가 생기면 이 시험이 깨진다), 처리한 건 숨기기(같은 status·updatedAt이면 숨김, updatedAt이 바뀌면 다시 보임), 다음 건 = 맨 위, 200건 안내 판정, 키보드 무시 판정.
- `useTaskActions` 단위: 각 동작이 성공 true·확인창 취소 false·실패 false를 돌려주는지, `onOk` 감싼 동작 포함.
- `inbox` 페이지(`test/inbox-page.spec.ts`): 묶음 렌더, 고르기·쿼리 반영, 상태별 본문 표의 각 줄(대표 버튼이 보이고 공용 동작을 부르는지), 성공 → 다음 건 이동·토글 끄면 머무름, 확인창 취소 → 머무름, 다른 곳에서 처리됨 → “처리할 것이 없는 상태”, `INTERVIEWING`이면 패널 유지, 쓰던 답변이 건 전환 뒤에도 남음, 입력칸 안의 `j`/`k` 무시, 폰 폭(`setViewportWidth`)에서 창 열기·자동 이동·마지막 건 뒤 창 닫힘, 200건 안내.
- 기존 시험 무수정 통과: `test/task-detail-*.spec.ts` 전부, `ApproveDialog.spec.ts`, `InterviewPanel.spec.ts`.
- `layout-default.spec.ts`: 관리자 위 탭·5칸 하단 바·배지 위치, 관리자 아닌 사람은 그대로. `auth-middleware.spec.ts`: `/inbox` 관리자 검사.
- 하이드레이션 스모크: `npm run build && npm run test:hydration` 통과(새 경로 포함, “목 응답이 없어 null로 답한 API” 없음).
- 린트: `npm run lint` 경고를 늘리지 않는다.

## 9. 배포

- 프론트만: `frontend/.output` 재빌드(사용자 승인 뒤). API·워커·인터뷰 서비스는 재기동하지 않는다. 라이브 재기동은 작업 스케줄러 `netisMaker-public` 경유(도구 셸에서 직접 기동 금지), 옛 빌드는 `.output.bak-<커밋>`으로 보관.

## 10. 구현자에게 맡기는 것

- 목록·처리 영역의 정확한 폭·여백·글자 크기(지금 작업 목록·상세의 모양을 따른다).
- 공용 모듈 함수의 정확한 이름과 인자 모양(§7의 받아들이는 기준을 지키는 범위에서).
- `draft` 묶기 방법(prop + emit이든 `defineModel`이든).
- 상태별 본문에서 보조 버튼의 배치·순서.
- 계획(plan)의 작업 순서. 단, **껍데기(목록·고르기·자동 이동) + 인터뷰 세 상태(입력대기·플랜승인대기·승인대기)가 처음부터 끝까지 돌아가는 상태를 먼저** 만들고, 나머지 상태는 그 뒤에 더한다.

## 11. 알려진 제한 · 후속

- 작업이 늘어 최근 변경 200건 밖에 확인 필요 건이 생기면 처리함에 안 보인다(안내는 뜬다). 그때는 서버에 상태 여러 개 거르기(`status` 여러 값)를 더하는 작은 변경으로 푼다.
- 일반 사용자 폰 “작업” 배지는 여전히 순서 없는 최근 50건 기준이다(이번에 안 고침).
- 목록 응답에 배포·구현 로그가 함께 실려 200건 폴링은 무겁다(작업 목록 화면도 같다). 문제가 되면 목록용 가벼운 응답을 따로 둔다.
- 위 탭 배지는 경로가 바뀔 때만 다시 센다.

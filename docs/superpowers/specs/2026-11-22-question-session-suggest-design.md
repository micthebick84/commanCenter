# 질문 세션 대화 중 제안 — DB 연결 · 참조 레포 설계

- 날짜: 2026-11-22
- 상태: 구현됨
- 범위: 인터뷰 서비스(Node) + 백엔드(Java, API 프로파일) + 프론트엔드(Nuxt). 워커는 바꾸지 않는다
- 선행 스펙: `2026-11-20-question-repo-route-design.md`(추천 카드, 이 문서는 그 §10 "2단계 윤곽"을 대신한다), `2026-10-02-question-db-mcp-design.md`(질문 DB 연결), `2026-10-22-question-ref-repos-design.md`(참조 repo), `2026-11-03-interview-mockups-design.md`(내장 SDK MCP 도구 선례)

## 1. 목적

추천 카드(1단계)는 세션을 만들기 전에 Jev가 **질문 문장만** 보고 "DB가 필요해 보이는가"를 추정한다. 그런데 DB가 필요한지, 다른 레포를 봐야 하는지는 대개 **소스를 읽어 봐야** 알 수 있다(예: 화면 값이 설정 테이블에서 온다, 호출하는 API가 다른 레포에 있다). 소스를 읽는 것은 세션이 시작된 뒤의 Claude뿐인데, 지금은 Claude가 그렇게 판단해도 사용자에게 알릴 방법이 답변 글밖에 없고, 사용자는 메뉴를 열어 직접 연결을 찾아 붙여야 한다.

이 기능은 질문 세션의 Claude가 답하는 도중 **"DB 연결이 있으면 더 정확히 답할 수 있다" / "이 레포도 봐야 한다"** 를 도구로 알리게 하고, 답변 아래 카드에서 버튼 한 번으로 붙여 같은 대화를 이어가게 한다.

## 2. 목표 · 비목표 · 반목표

**목표**
- 질문 세션의 Claude가 코드를 읽다가 필요하다고 판단하면 DB 연결 또는 참조 레포를 제안할 수 있다.
- 제안은 그 답변 아래 카드로 보이고, 이유가 함께 적힌다.
- 사용자가 카드에서 고르고 버튼을 누르면 연결·참조가 붙고 같은 대화에서 이어서 답한다.
- 제안과 그 결과(붙였는지·닫았는지)를 기록해 나중에 판단 품질을 볼 수 있다.
- 제안할 것이 없는 세션(붙일 수 있는 연결·레포가 없음, 기능 꺼짐)은 프롬프트·옵션·보고 바디가 지금과 바이트까지 같다.

**비목표 (이번 범위 밖)**
- 추가 질문을 보내기 **전에** Jev로 다시 판정하는 것(선행 스펙 §10의 원래 윤곽). 기록을 본 뒤 따로 판단한다.
- 작업 인터뷰(INTERVIEW)·구현·디자인 세션의 제안. 질문 세션(QUESTION)만.
- 대상 레포 바꾸기, 새 질문으로 갈아타기 제안.
- MCP 도구(카탈로그 MCP) 제안.
- DB 접속정보 등록을 카드 안에서 하는 것. 붙일 연결이 없는 레포에는 DB 제안 자체가 생기지 않는다.

**반목표 (이렇게 되면 기능은 돌아가도 실패)**
- 사용자가 누르지 않았는데 연결·참조가 붙는 것. Claude는 제안만 하고 붙이는 것은 언제나 사용자의 버튼이다.
- 제안 도구가 읽기 전용 경계를 넓히는 것(쓰기·실행·경로 밖 읽기).
- Claude가 답을 미루고 제안만 내는 것. 제안을 해도 코드만으로 할 수 있는 답은 그 턴에 끝낸다.
- DB 접속정보(호스트·계정·비밀번호)나 카탈로그의 내부 설명(담당자 이름 등)이 프롬프트·제안 본문에 실리는 것.
- 답변마다 습관적으로 제안이 붙어 카드가 소음이 되는 것.

## 3. 제약 (코드에서 확인한 것)

- 질문 턴은 `interviewRunner.ts`의 `runQuestionTurn`이 SDK `query` → `relay` → `postQuestion`(바디 `WorkerQuestionRequest`)으로 끝낸다. 내장 SDK MCP 서버를 턴마다 만드는 선례가 둘 있다: DB(`dbMcp.ts`, `db-<id>`)와 인터뷰 목업(`mockupMcp.ts`, `mockup`).
- 질문 게이트는 기본 도구에는 default-deny지만 MCP에는 아니다: `questionMcpGate`(`permissions.ts`)는 Obsidian 계열(읽기 도구 allowlist)·내장 DB 서버(`db-<id>`, SQL 검사)만 따로 보고, 그 밖의 서버는 도구 이름에 쓰기·실행 동사가 있을 때만 막는다. 그래서 새 내장 서버의 도구 이름은 지금 게이트를 그대로 통과한다.
- 세션의 MCP 서버는 운영자 `~/.claude.json` 스냅샷(`mcpsBase`) → 카탈로그 extras → 내장 서버 순으로 합쳐진다(`sessionOptions.ts`). 같은 이름이면 뒤가 이긴다.
- 대화 화면은 보낼 때마다 초안 전체(모델·추론·MCP·DB·참조·첨부)를 싣는다(`pages/questions/[id].vue`). `InterviewPanel`의 `sendAnswer`는 입력창의 글만 보내고 밖에서 부를 수 없다.
- `/api/db-connections`는 **보는 사람** 기준으로 거른다(관리자는 모든 레포 공용 연결 + 자기 개인 연결). 반면 `ask`의 DB 검증은 **세션 요청자** 기준이다(`validateSelection`).
- `resolveReferences`는 지원하지 않는 호스트의 레포와, 브랜치를 주지 않았는데 기본 브랜치가 없는 레포를 400으로 거절한다.
- 대화 중 DB·참조 변경 경로는 이미 있다: `POST /api/questions/{id}/ask` 바디 `dbConnectionIds`·`refRepos`(null=유지, 같은 집합이면 no-op, 상한 각 3개) → `QuestionService.applyDbChange`·`applyRefChange`가 검증하고 `system/note` 턴을 남긴다. 다음 claim부터 반영된다.
- 문답 상한 `app.question.max-qa-turns`(기본 10)는 `ask`가 센다. 제안을 받아들여 다시 묻는 것도 한 턴이다.
- 답변은 SSE `question` 이벤트와 스냅샷(`InterviewResponse.turns`)으로 화면에 간다. 목업은 별도 이벤트 `mockup`으로 간다(`InterviewStreamService.pushMockup`).
- DB 연결 선택 가능 여부는 `DbConnectionService.validateSelection(repoCatalogId, ownerId, ids)`가 정한다(레포 공용 + 그 사용자의 개인 연결). DB 기능은 암호화 키가 없으면 꺼진다(`isEnabled`).
- 참조 선택 검증은 `RepoCatalogService.resolveReferences`(대상과 다른 레포, 중복 불가, 최대 3).
- 카탈로그의 `route_hint`(추천 키워드)는 관리자만 보는 칸이고 외부 모델에 보내도 되는 내용만 담기로 한 칸이다. `description`에는 담당자 이름이 들어 있을 수 있다.

## 4. 접근

세 가지를 놓고 사용자가 B를 골랐다(2026-11-22).

| 방안 | 판단 주체 | 소스를 보고 판단 | 버린 이유 / 고른 이유 |
|---|---|---|---|
| A. 추가 질문을 보내기 전에 Jev로 다시 판정 | Jev(질문 문장) | 아니오 | 지금의 한계(문장만 봄)가 그대로다. 기준값을 정할 기록도 아직 없다 |
| **B. 답변 중 Claude가 도구로 제안** | 질문 세션의 Claude | 예 | 소스를 읽은 쪽이 판단한다. 붙이는 경로는 이미 있어 새 변경 경로가 없다 |
| C. A + B | 둘 다 | 일부 | 제안이 두 군데서 나오고 작업량이 가장 크다. B의 기록을 본 뒤 A를 판단한다 |

B의 비용은 **한 턴**이다. Claude는 코드만으로 답을 먼저 내고 제안하므로, 붙인 뒤 한 번 더 돈다.

## 5. 동작

### 5.1 흐름

1. API가 질문 세션 claim에 **제안 후보**를 싣는다(§6.1). 후보가 하나도 없으면 싣지 않는다.
2. 인터뷰 서비스가 후보가 있을 때만 내장 MCP 서버 `suggest`를 붙이고 프롬프트에 제안 절을 더한다(§7).
3. Claude가 답하는 중 필요하면 `suggest_db` / `suggest_ref_repo`를 부른다. 도구는 그 턴의 메모리에만 모으고, 외부에 아무것도 하지 않는다.
4. 턴이 끝나면 답변 보고(`postQuestion`)에 `suggestions`를 함께 싣는다. 없으면 키 자체를 생략한다.
5. API가 검증·정규화해 `com.question_suggestion`에 저장하고(§6.2), 답변과 함께 화면에 보낸다.
6. 화면이 그 답변 아래에 제안 카드를 그린다(§8).
7. 사용자가 고르고 `연결하고 다시 묻기`를 누르면 화면이 기존 `ask`를 부른다 — 붙일 연결·참조를 바디에 싣고, 정해진 이어 묻기 문장을 `answer`로 보낸다(§6.3).
8. 다음 턴에 Claude는 붙은 DB·참조를 쓸 수 있다(기존 동작).

### 5.2 제안 하나의 모양

| 종류 | Claude가 주는 것 | 화면에 보이는 것 |
|---|---|---|
| DB | 이유(필수, 200자 이하), 보고 싶은 테이블·대상 이름(선택, 5개 이하), 후보 중 고른 연결 id(선택) | "DB 연결이 있으면 더 정확히 답할 수 있습니다" + 이유 + 붙일 수 있는 연결 목록(Claude가 고른 것이 미리 체크) |
| 참조 레포 | 이유(필수, 200자 이하), 후보 중 고른 레포 id(필수) | "이 레포도 함께 보면 좋습니다: {별칭}" + 이유 |

한 턴에 DB 제안은 1개, 참조 제안은 2개까지 받는다. 넘는 호출은 도구가 "이미 제안했다"고 돌려준다. 같은 대상의 중복도 같다.

### 5.3 받아들였을 때

- 이어 묻기 문장(고정, 화면이 만든다): DB만 `방금 연결한 DB로 확인해서 앞의 답을 보완해 주세요.` / 참조만 `방금 추가한 참조 레포를 보고 앞의 답을 보완해 주세요.` / 둘 다 `방금 연결한 DB와 추가한 참조 레포를 보고 앞의 답을 보완해 주세요.`
- 참조 레포의 브랜치는 카탈로그의 기본 브랜치다. 다른 브랜치가 필요하면 지금의 `참조 변경`을 쓴다.
- 이미 3개가 찬 종류는 카드에서 고를 수 없고 사유를 보인다(`DB 연결은 3개까지` / `참조 레포는 3개까지`).
- 문답 상한에 닿은 세션은 버튼이 꺼지고 기존 안내(새 질문 세션을 열어 달라)를 보인다. API는 그런 턴의 claim에 후보를 싣지 않는다(다음 턴이 없으므로).
- 붙이는 검증은 기존 `ask`가 그대로 한다. 그사이 연결이 지워졌거나 꺼졌으면 `ask`가 400을 주고 화면은 그 사유를 보통 전송 실패와 같은 알림으로 보인다(카드는 그대로 남는다).

### 5.4 받아들이지 않았을 때

- `닫기`를 누르면 그 제안은 `DISMISSED`가 되고 카드가 접힌 한 줄(`제안: DB 연결 — 닫음`)로 남는다.
- 사용자가 카드를 두고 다른 추가 질문을 보내면 남은 `PENDING` 제안은 `SUPERSEDED`가 된다(같은 한 줄 표기, `연결하지 않음`). 지난 답변의 제안은 다시 누를 수 없다 — 그때의 후보가 지금도 맞는지 알 수 없다.
- 세션이 종료·만료돼도 제안 행은 기록으로 남는다.

## 6. 백엔드 (API)

### 6.1 claim에 싣는 후보

`InterviewClaimResponse`에 선택 필드 `suggest`를 더한다. 질문 세션이고, 기능이 켜져 있고(`app.question.suggest.enabled`, 기본 true), 이번 턴 뒤에 문답이 한 번 이상 남았을 때만 채운다.

- `dbCandidates`: `[{id, name, dbType}]` — 대상 레포에서 **요청자**가 고를 수 있는 연결(`validateSelection`과 같은 기준) 중 세션에 아직 안 붙은 것. DB 기능이 꺼졌거나 세션에 이미 3개가 붙었으면 빈 목록. 접속정보는 싣지 않는다(이름·종류만).
- `refCandidates`: `[{catalogId, alias, hint}]` — 켜진 카탈로그 항목 중 대상이 아니고 세션에 아직 참조로 안 붙은 것. **기본 브랜치로 `resolveReferences`를 통과할 항목만**이다(지원하는 호스트, 기본 브랜치 있음) — 받아들이면 반드시 붙을 수 있는 것만 알린다. `hint`는 `route_hint`(없으면 생략)이고 `description`은 싣지 않는다. 이미 3개가 붙었으면 빈 목록.
- 두 목록이 모두 비면 `suggest` 자체를 생략한다.
- 후보 계산은 한 곳에 두고 claim·제안 보고 검증(§6.2)·화면용 선택지(§6.2 끝)가 함께 쓴다.

### 6.2 제안 저장 — `com.question_suggestion` (V48)

| 칸 | 내용 |
|---|---|
| `id`, `session_id`(FK, CASCADE), `turn_seq` | 어느 답변에 붙은 제안인지 |
| `kind` | `DB` \| `REF_REPO` |
| `db_connection_id`(FK, SET NULL), `repo_catalog_id`(FK, SET NULL) | 대상(DB는 Claude가 고르지 않았으면 NULL) |
| `reason` | 200자 이하 |
| `targets` | JSONB 문자열 배열(DB만, 보고 싶은 테이블 이름) |
| `status` | `PENDING` \| `ACCEPTED` \| `DISMISSED` \| `SUPERSEDED` |
| `decided_at`, `decided_by`, `created_at` | |

`WorkerQuestionRequest.suggestions`(선택)를 `recordQuestion`이 처리한다. 러너의 출력을 그대로 믿지 않는다:
- 질문 세션이 아니면 무시한다.
- 대상 id가 **지금** 후보 기준(§6.1과 같은 계산)에 맞지 않는 제안은 버린다. DB 제안에서 고른 연결만 틀렸으면 연결 없는 DB 제안으로 받는다.
- 개수 상한(§5.2)을 넘는 것은 버리고, `reason`·`targets`는 길이를 자르고 비밀 가리기(`GitRemotes.mask`·`SecretMasks`)를 거친다. `reason`이 비면 그 제안은 버린다.
- 저장은 답변 턴이 **커밋된 뒤** 별도 트랜잭션에서 한다(워커 컨트롤러가 부르고 예외를 잡아 경고만 남긴다) — 제안 때문에 답변 보고가 실패하면 안 된다. 같은 트랜잭션 안에서는 후보 계산이 거치는 다른 서비스의 예외가 트랜잭션을 롤백 전용으로 만들어, 잡아도 답변 커밋이 실패한다. 화면용 제안 조회도 같은 이유로 질문 조회 트랜잭션 밖(컨트롤러)에서 붙이고, 실패하면 제안 없이 응답한다.

화면 전달: 스냅샷 `InterviewResponse.suggestions`(세션의 모든 제안, 턴 seq·상태 포함)와 실시간 SSE 이벤트 `suggestion`(답변 이벤트 뒤에 보낸다). 본인·관리자만 본다(세션 조회 권한 그대로).

`PENDING`인 DB 제안에는 **지금 붙일 수 있는 연결 선택지**(`dbOptions`: `[{id, name, dbType}]`)를 함께 싣는다 — 보는 사람이 아니라 **세션 요청자** 기준으로, 조회할 때마다 §6.1과 같은 계산으로 만든다. 관리자가 남의 세션을 볼 때도 `ask`가 받아 줄 연결만 보이고, 요청자의 개인 연결은 이름·종류만 보인다. `PENDING`인 참조 제안에는 별칭과 기본 브랜치를 싣는다. 남은 자리 수(`dbSlotsLeft`·`refSlotsLeft`, 3 − 붙은 수)도 함께 준다.

### 6.3 받아들이기·닫기

- `QuestionAskRequest`에 선택 필드 `acceptSuggestionIds`를 더한다. `ask`가 답변 턴·연결 변경과 **같은 트랜잭션**에서 그 id들을 `ACCEPTED`로 바꾼다. 이 세션의 `PENDING`이 아닌 id는 조용히 무시한다(붙이는 것은 `dbConnectionIds`·`refRepos`가 하고, 이 칸은 기록만 한다).
- 같은 `ask`에서, 새 사용자 턴이 생길 때 이 세션에 남은 다른 `PENDING` 제안은 `SUPERSEDED`로 바꾼다.
- 닫기: `POST /api/questions/{id}/suggestions/{sid}/dismiss` — 질문할 수 있는 사람(본인·관리자)만, `PENDING`일 때만(아니면 409).

### 6.4 예약 이름

MCP 카탈로그 이름 `suggest`는 `db-*`처럼 예약한다(등록·수정 400). 운영자 `~/.claude.json`에 같은 이름의 서버가 있어도 내장 서버가 마지막에 합쳐져 이긴다(후보가 있는 턴에서만 가려진다) — 인터뷰 서비스는 기동 때 그 이름이 스냅샷에 있으면 경고를 한 줄 남긴다.

## 7. 인터뷰 서비스

- 새 파일 `src/sdk/suggestMcp.ts`: `createSuggestMcp(candidates)` → 내장 서버 `suggest`와 수집 함수. 도구는 후보가 있는 종류만 만든다(`suggest_db`는 `dbCandidates`가, `suggest_ref_repo`는 `refCandidates`가 비지 않을 때). 입력은 zod로 검증하고, 후보에 없는 id는 `isError` 결과로 돌려준다(예외 없음, `dbMcp.ts`·`mockupMcp.ts`와 같은 모양). 성공 결과 문구는 "제안을 남겼습니다 — 사용자가 연결하면 다음 답변부터 쓸 수 있습니다. 지금은 코드로 확인한 범위에서 답을 마무리하세요."
- `runQuestionTurn`: `claim.suggest`가 있으면 서버를 만들어 옵션의 MCP 서버에 더하고, 프롬프트 접두에 제안 절을 더하고, `postQuestion` 바디에 수집한 `suggestions`를 싣는다(없으면 키 생략). 턴이 실패하면 보고하지 않는다(`refStates`와 같다).
- 게이트: 코드를 바꾸지 않는다 — 두 도구 이름(`mcp__suggest__suggest_db`·`mcp__suggest__suggest_ref_repo`)은 지금의 `questionMcpGate`를 통과한다(쓰기·실행 동사 없음). 이름이 앞으로 denylist에 걸리지 않게 시험 하나로 고정한다. 서버가 붙지 않은 턴에는 도구 자체가 없다. 내장 서버는 `mcpsBase`·extras **뒤에** 합친다(§6.4).
- 제안 절(매 턴 접두, 후보가 있을 때만)에 담는 규칙:
  - 언제 부르는가 — DB: 코드를 읽어 보니 답이 **실제 DB의 구조나 저장된 값**에 달려 있고 지금 연결된 DB로는 볼 수 없을 때만. 참조: 답이 목록의 **다른 레포 코드**에 달려 있을 때만(호출 대상·공유 모듈 등 근거를 코드에서 확인했을 때).
  - 추측으로 부르지 않는다. 한 답변에 종류별 한 번이면 충분하다.
  - 부른 뒤에도 코드만으로 확인한 답은 끝까지 쓰고, 확인하지 못한 부분이 무엇인지 한 문장으로 밝힌다.
  - 후보 목록(DB: `id · 이름 · 종류`, 레포: `id · 별칭 · 키워드`).
- 후보가 없는 claim(구버전 API 포함)에서는 서버·절·바디 키가 모두 없다 — 지금과 바이트까지 같다(시험으로 지킨다).

## 8. 프론트엔드

- 제안 카드는 **가장 최근 답변** 아래, 그 답변에 `PENDING` 제안이 있을 때만 뜬다. 입력 대기 상태가 아니면(답변 중·종료됨) 버튼이 꺼진다.
- 카드 한 장에 그 답변의 제안을 모은다: DB 줄(이유, 보고 싶은 테이블, 연결 체크박스 목록)과 참조 줄(별칭, 이유, 체크박스). 참조 제안은 남은 자리까지 미리 체크된다(기본 브랜치가 없는 것은 제외). 버튼은 `연결하고 다시 묻기`(체크된 것이 있을 때만 켜짐)와 `닫기`.
- DB 연결 목록은 제안에 실려 온 선택지(`dbOptions`, §6.2)로 그린다 — `/api/db-connections`는 보는 사람 기준이라 관리자가 남의 세션을 볼 때 어긋난다. Claude가 고른 연결이 선택지에 있으면 미리 체크하고, 없으면 선택지가 하나일 때만 그것을 체크한다. 선택지가 비었으면(그사이 연결이 지워짐 등) DB 줄은 `붙일 수 있는 연결이 없습니다`로 바뀐다.
- 체크할 수 있는 수는 남은 자리 수까지다(`dbSlotsLeft`·`refSlotsLeft`). 넘으면 나머지 체크박스가 꺼지고 사유를 보인다.
- `연결하고 다시 묻기`는 **보통의 전송과 같은 바디**로 보낸다 — 화면에 보이는 초안(모델·추론·MCP·DB·참조) 그대로에 고른 연결·참조를 더하고(`dbConnectionIds` = DB 초안 + 고른 것, `refRepos` = 참조 초안 + 고른 것·기본 브랜치), `acceptSuggestionIds`를 싣고, `answer`만 §5.3의 고정 문장으로 바꾼다. 화면에 보이는 칩과 보내는 값이 같아야 하기 때문이다. **입력창에 쓰던 글과 아직 안 보낸 첨부는 보내지 않고 그대로 둔다**(다음 전송 때 쓴다).
- 이를 위해 `InterviewPanel`의 전송 함수가 글을 인자로 받을 수 있어야 하고(입력창을 건드리지 않는 경로), 카드가 그것을 부를 수 있어야 한다. 전송 뒤 DB·참조 초안은 지금처럼 서버 값으로 다시 맞춰진다.
- 지난 제안은 접힌 한 줄로 남는다(§5.4).
- 좁은 화면에서도 같은 카드다. 클래스 이름은 Quasar 반응형 표시 헬퍼 이름과 겹치지 않게 한다(CLAUDE.md).
- `scripts/hydration-smoke.mjs`의 질문 상세 목에 `suggestions`를 더한다.

## 9. 안전 · 운영

- 읽기 전용 경계: 새 도구는 메모리에 적기만 한다. 파일·네트워크·DB에 닿지 않는다. 붙이는 일은 사용자의 `ask`가 기존 검증으로 한다.
- 프롬프트로 나가는 새 정보: DB 연결의 이름·종류, 다른 레포의 별칭·추천 키워드. 접속정보와 카탈로그 설명은 나가지 않는다.
- 끄기: `APP_QUESTION_SUGGEST_ENABLED=false` + API 재기동 → claim에 후보가 없어 전부 예전 동작.
- 배포 순서: API(V48, 병합 직전 main 최대 번호 확인) → 인터뷰 서비스(재기동만) → 프론트(`.output` 재빌드). 어느 순서로 어긋나도 안전하다 — 구 API는 후보를 안 보내고 모르는 바디 칸을 버리며, 구 러너는 후보를 무시하고, 구 화면은 제안을 안 그릴 뿐이다.
- 확인할 것(배포 뒤 실제 사용): 제안이 얼마나 자주 붙는지(답변 수 대비), 받아들인 비율, 받아들인 뒤 답이 실제로 달라졌는지. 소음이면 제안 절의 규칙을 조이거나 끈다.

## 10. 사용자 결정 · 내 결정

**사용자 결정 (2026-11-22)**
- 방안 B(답변 중 Claude가 제안).
- DB 연결 제안과 함께 참조 레포 제안도 넣는다.

**내 결정 (반대하면 바꾼다)**
- 질문 세션만 대상. 작업 인터뷰는 관리자가 승인 때 DB·참조를 정하는 흐름이 따로 있다.
- 받아들이면 자동으로 이어 묻는다(고정 문장). "붙이기만 하고 직접 다시 묻기"는 지금의 DB 메뉴·`참조 변경`으로 이미 된다.
- 붙일 연결이 없는 레포에는 DB 제안을 만들지 않는다(등록 안내 카드 없음).
- 다른 레포 후보는 별칭 + 추천 키워드로 알린다. 카탈로그 설명은 담당자 이름이 있을 수 있어 싣지 않는다.
- 제안은 표에 따로 저장한다(턴의 JSON 칸이 아니라) — 얼마나 제안했고 얼마나 받아들였는지 SQL로 바로 본다.
- 지난 답변의 제안은 다시 누를 수 없다.
- 한 턴의 상한: DB 1개·참조 2개, 이유 200자.
- 받아들일 때 입력창에 쓰던 글·안 보낸 첨부는 보내지 않고 남긴다. 모델·MCP·DB·참조 초안은 보통 전송처럼 함께 간다.
- 관리자가 남의 세션에서 받아들일 때도 선택지는 요청자 기준이다(요청자의 개인 연결은 이름·종류만 보인다).
- 받아들이면 반드시 붙는 후보만 Claude에게 알린다(기본 브랜치 없는 레포·지원하지 않는 호스트 제외).
- 구현 중 정함: 제안은 답변 트랜잭션이 커밋된 뒤 별도 트랜잭션에 저장하고(워커 컨트롤러가 호출), 화면용 제안 뷰는 컨트롤러가 트랜잭션 밖에서 붙인다 — 다른 서비스의 예외가 바깥 트랜잭션을 롤백 전용으로 만들기 때문.
- 구현 중 정함: 참조 제안은 카드에서 남은 자리까지(순서대로, 기본 브랜치 없는 것 제외) 미리 체크한다. DB는 Claude가 고른 연결(또는 선택지가 하나면 그것)만 미리 체크한다.

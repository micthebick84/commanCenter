# 종료 부분 패치(변경 파일만, 배포 폴더 구조) 설계

- 날짜: 2026-11-10
- 상태: 사용자 검토 대기. 사용자가 정한 것은 §3, 작성자 판단은 §13에 모았다.
- 범위: netisMaker API·워커 데몬·프론트, DB(V43). 인터뷰 서비스 변경 없음.
- 근거: 종료 산출물 `2026-10-14-close-artifact-delivery-design.md`, 납품 파일 `2026-11-04-close-artifact-bundle-design.md`, 미리 빌드 `2026-10-28-deploy-prebuild-design.md`.

## 1. 문제

종료 산출물은 WAR·zip 전체(수백 MB)다. 현장에는 보통 작업 하나만큼의 변경만 내보내면 되는데, 지금은 사람이 바뀐 소스를 찾아 빌드 결과에서 `.class`·JSP를 골라 배포 폴더 구조로 손수 묶는다. 빠뜨리기 쉽고(내부 클래스, 상수를 쓰는 다른 클래스) 시간이 든다.

## 2. 목표·비목표·피해야 할 것

목표
- 작업을 종료하면 그 작업이 바꾼 **배포 파일만** 든 zip이 자동으로 만들어져 보관된다.
- zip 안은 **배포 폴더 구조**다. 자바 소스는 `.class`로 들어간다(예: `WEB-INF/classes/com/foo/Bar.class`).
- 작업 목록(작업종료)과 작업 상세에서 버튼 하나로 `날짜_패치내용.zip`을 내려받는다.

비목표
- 이미 종료된 작업의 패치 만들기(기능을 켠 뒤 종료 승인하는 작업부터).
- 여러 작업을 묶은 누적 패치, 현장에 깔린 버전 기록·추적.
- 패치를 현장에 적용하는 스크립트, 현장별 프로파일마다 다른 패치.
- 새 빌드 툴체인 추가(지금 있는 `jdk8-maven`과 카탈로그 명령을 그대로 쓴다).
- 종료 산출물(전체 WAR·zip) 기능의 동작 변경.

피해야 할 것(돌아가도 실패로 본다)
- 바뀐 배포 파일이 빠진 패치가 정상처럼 내려받아지는 것.
- 빌드 시각 같은 잡음 때문에 안 바뀐 파일(특히 `WEB-INF/lib`의 jar 수백 개)이 패치에 실리는 것.
- 패치 단계 실패로 종료를 끝낼 방법이 없어지는 것.
- 부분 패치를 켜지 않은 레포·작업의 종료 흐름·시간이 달라지는 것.

## 3. 사용자가 정한 것

1. 패치 범위 = 고른 작업(커밋)의 변경. **현장은 언제나 그 커밋 바로 앞 상태라고 가정한다.**
2. 화면: **작업종료 목록에 부분 패치 버튼**, 누르면 `날짜_패치내용.zip`이 내려받아진다.
3. zip은 배포 폴더 구조, 자바는 `.class`.
4. **종료할 때 미리 만든다**(버튼은 보관된 파일을 바로 받는다).
5. 방식은 "패치 전·후를 각각 빌드해 결과물을 비교"(§4). 소스 변경 목록을 규칙으로 옮기는 방식·바뀐 파일만 `javac` 하는 방식은 간접 변경(상수 인라인, 내부 클래스, 생성 코드)을 놓쳐 기각.
6. 아래는 작성자가 제안하고 사용자가 확인한 것: 카탈로그 체크로 켜고 끔(미리 빌드 명령이 있는 레포만), 병합 직후 단계, "후" 해시 목록 보관으로 다음 빌드 생략, 실패 시 종료실패 + 재시도 / "패치 없이 마무리", WAR 여러 개면 WAR별 폴더, 바뀐 jar는 통째로, 삭제 목록·명세 포함, 변경 없으면 "변경 없음" 표시, 이미 종료된 작업 제외.

## 4. 동작 개요

```
종료 승인 ─ 패치 대상이면 task.close_patch_mode = REQUIRED
워커 종료 처리
  ① 병합                      → merge_commit_sha
  ② 부분 패치 (새 단계 PATCH_BUILT)
       "후" = 병합 커밋,  "전" = 병합 커밋의 첫 번째 부모
       전·후를 각각 카탈로그 미리 빌드 명령으로 빌드 → 비교 대상 파일을 풀어 내용 비교
       → 바뀐·추가된 파일 + 삭제 목록 + 명세 → zip → API로 업로드
  ③ 배포 중지 → ④ 산출물(있으면) → ⑤ 노트 → ⑥ 브랜치 삭제   (지금과 같음)
작업 목록·상세: [부분 패치] 버튼 → 1회용 주소 → 내려받기
```

## 5. 대상 판정(API, 종료 승인 때 한 번)

`close_patch_mode = REQUIRED` 조건(모두 참):
- 전역 스위치 `app.close.patch.enabled`(`CLOSE_PATCH_ENABLED`, 기본 false).
- 카탈로그 `patch_enabled = true`, 그리고 `prebuild_command`가 비어 있지 않음. (`prebuild_enabled`는 보지 않는다 — 배포 미리 빌드를 끈 레포도 명령만 있으면 패치를 만들 수 있다.)
- 작업 타입이 `DB_WORK`가 아님.

아니면 null(지금과 같은 흐름). 관리 화면은 `prebuild_command`가 비었는데 `patch_enabled`를 켜면 저장을 거절한다.

`CloseStep`에 `PATCH_BUILT`를 `MERGED` 바로 뒤에 넣고, `required(...)`가 패치 모드도 받아 REQUIRED일 때만 필요 단계로 본다. `SKIPPED`(관리자 "패치 없이 마무리")면 필요 단계에서 빠진다.

claim에는 `closePatch` 스펙(명령, 툴체인, 비교 대상 경로, 파일 이름에 쓸 제목·날짜)이 실린다. REQUIRED가 아니거나 단계가 끝났으면 null.

## 6. 워커: 패치 만들기

### 6.1 전·후 커밋
- "후" = 병합 결과 커밋(`merge_commit_sha`). "전" = **병합 직전 기준 브랜치 끝**.
- 워커는 병합 **직전에** 원격 기준 브랜치 끝 sha를 읽어 두고, MERGED 진행 보고에 `baseSha`로 함께 보낸다 → API가 `task.patch_base_sha`에 기록(재시도 claim의 `closePatch.baseSha`로 다시 받는다).
- 패치 단계는 시작할 때 **검증**한다. 하나라도 어긋나면 빌드 없이 단계 실패(사유 `패치 기준 커밋을 확인할 수 없습니다: …`) — 틀린 범위의 패치가 정상처럼 나가지 않게 한다.
  1. `merge_commit_sha`가 있다(코드상 null일 수 있다 — GitLab fast-forward 프로젝트, 사람이 미리 병합한 경우 등).
  2. `baseSha`가 기록돼 있으면 `후^1 == baseSha`(merge·squash 병합에서 성립. 그 사이 기준 브랜치에 다른 push가 끼었으면 어긋난다).
  3. `baseSha`가 없으면(사람이 미리 병합해 워커가 병합 직전을 못 본 경우) "후"가 **부모 둘인 병합 커밋일 때만** `후^1`을 "전"으로 쓴다. 부모가 하나면 실패.
- `CLOSE_MERGE_METHOD=rebase`(GitHub)는 지원하지 않는다 — 병합 **전에** "부분 패치는 rebase 병합을 지원하지 않습니다"로 종료실패(지금 `requireVault()`처럼 되돌릴 수 없는 병합 앞에서 확인). 미리 빌드 툴체인이 워커에 설정돼 있는지도 같은 자리에서 확인한다. GitLab은 rebase를 merge로 취급하므로 해당 없음.
- 레포 캐시는 `--depth=1`이라 "전"·"후" 두 커밋을 따로 fetch 한다(참조 repo의 고정 커밋 받기와 같은 방식). 전·후 각각 detached worktree를 만들고 끝나면 성공·실패 모두 지운다. 폴더 이름은 worktree 정리 잡 규칙(`WorktreeKind`)에 맞춘다.

### 6.2 빌드
- 카탈로그 `prebuild_command`·`prebuild_toolchain`으로 `DeployPrebuilder`와 **같은 방식**(툴체인 env, 셸, 스택 비밀 제거, 스트리밍 로그)으로 실행한다. 실행 부분을 공용으로 빼서 쓴다.
- 비교 대상 파일(§6.3)을 worktree에서 찾는다. 빌드 실패·대상 없음이면 단계 실패.
- 빌드 한 번의 상한은 미리 빌드와 같은 값(기본 20분). 전·후는 차례로 돈다(동시 실행 안 함 — 로컬 Maven 저장소 경합 회피).
- 종료에는 화면으로 가는 로그 통로가 없다. 빌드 출력은 워커 로그에 남기고, 실패하면 출력 끝부분(비밀 가린 뒤)을 실패 사유에 싣는다. 빌드 중 화면에는 종료 단계 목록의 "부분 패치"가 진행 중으로만 보인다.
- "전" 커밋이 지금 카탈로그 명령으로 빌드되지 않으면(명령이 생기기 전 커밋 등) 단계 실패다. 출구는 "패치 없이 마무리".

### 6.3 비교 대상
우선순위:
1. 빌드가 `.netis-artifact/`에 파일 하나를 만들었으면 그 파일(납품 파일 — 경북대의 두 캠퍼스 war zip).
2. 아니면 카탈로그 `prebuild_artifact`가 가리키는 파일 하나.

풀기 규칙:
- `.war`·`.jar` 하나 → 그 안의 항목이 곧 배포 경로. zip 안 `patch/` 바로 아래에 둔다.
- `.zip`·`.tar.gz`·`.tgz` 묶음 → 안의 `.war`마다 `patch/<war 이름(확장자 뺌)>/` 아래에 그 war의 항목을 둔다. 묶음 안의 war가 아닌 파일은 `patch/<묶음 안 경로>`로 파일 단위 비교한다.
- **전·후의 모양이 같아야 한다**: 대상 종류(단일 war/jar인지 묶음인지)와 묶음 안 war 이름 집합이 다르면 비교하지 않고 단계 실패(`패치 전·후 빌드 결과의 구성이 다릅니다`). 전체 추가 + 전체 삭제로 된 수백 MB 패치가 정상처럼 나가는 것을 막는다. 해시 목록(§6.5)에도 이 모양을 함께 적는다.
- war 안의 **중첩 jar(`WEB-INF/lib/*.jar` 등)는 풀지 않는다.** 같은지 여부만 jar 안 항목 기준으로 판정하고(§6.4), 다르면 jar를 통째로 패치에 넣는다.

### 6.4 "같다"의 기준(잡음 제거)
- 일반 파일: 내용 SHA-256.
- jar(중첩 포함): 항목 이름 + 항목 내용 해시의 정렬된 목록이 같으면 같다. 항목 시각·압축 방식·순서는 무시.
- 무시 패턴(war 항목과 jar 안 항목 모두에 적용): 기본 `META-INF/MANIFEST.MF`, `META-INF/maven/**`. 워커 설정 `netis-maker.worker.close.patch.ignore`로 바꿀 수 있다. 무시된 항목은 비교에서도 패치에서도 빠진다.
- 검증 기준: **같은 커밋을 두 번 빌드해 비교하면 차이 0**이어야 한다. 구현 중 실제 레포(카탈로그 5·12·13 중 하나 이상)로 확인하고, 잡음이 남으면 무시 패턴을 더한다.

### 6.5 "후" 해시 목록 보관(빌드 한 번 줄이기)
- 패치 단계가 끝나면 "후"의 (배포 경로 → 해시) 목록을 워커 PC에 보관한다: `{reposDir의 형제}/close/patch-manifests/{repoKey}/{커밋 40자}-{키}.json`. 키 = 명령·툴체인·비교 대상 경로·무시 패턴의 해시.
- 다음 패치에서 "전" 커밋의 목록이 있으면 "전" 빌드를 건너뛴다("전"은 해시만 필요하다 — 파일은 "후"에서만 꺼낸다).
- 레포마다 최근 20개만 남긴다. 목록이 깨졌거나 못 읽으면 그냥 빌드한다.

### 6.6 결과
비교 결과가
- 바뀜·추가·삭제가 하나라도 있으면 zip을 만들어 업로드하고 `PATCH_BUILT` 보고.
- 하나도 없으면 업로드 없이 "변경 없음"으로 `PATCH_BUILT` 보고.

## 7. zip 구조와 이름

```
20261110_로그인_오류_수정.zip
├─ PATCH-INFO.txt
├─ DELETED.txt
└─ patch/
   ├─ WEB-INF/classes/com/foo/Bar.class
   ├─ WEB-INF/classes/com/foo/Bar$1.class
   ├─ WEB-INF/lib/hm-core-1.2.jar
   └─ jsp/login.jsp
(묶음이면 patch/hm-dash-daegu/…, patch/hm-dash-sangju/…)
```

- `PATCH-INFO.txt`(UTF-8): 작업 번호·제목, 레포 별칭, 패치 전·후 커밋(40자), **"이 패치는 '패치 전' 커밋 상태의 배포본에만 적용한다"** 경고, 만든 시각, 빌드 명령, 추가·변경·삭제 개수와 목록, 참고용 소스 변경 목록(`git diff --name-status 전 후`).
- `DELETED.txt`: 현장에서 지울 배포 경로, 한 줄에 하나. 없으면 `(없음)`.
- 파일 이름: `{yyyyMMdd}_{제목}.zip`. 날짜는 패치를 만든 날(KST). 제목은 작업 제목에서 `\ / : * ? " < > |`와 제어 문자를 빼고 공백을 `_`로, 60자까지. 비면 `task-{id}`. API가 claim에 실어 보낸 값을 워커가 쓴다(이름 규칙은 API 한 곳).

## 8. API

- 업로드: `PUT /worker/tasks/{id}/patch?workerId=&name=`(원시 본문, `X-Artifact-Sha256`) — 산출물 업로드와 같은 3단계(확인 → 트랜잭션 밖 파일 쓰기 → 잠금 뒤 기록), 조건은 상태 `CLOSING`·담당 워커·모드 REQUIRED. 크기 상한은 `app.close.patch.max-size-mb`(기본 1024).
- 보관: `{app.attachment.dir}/task-{id}/patch/{name}`(작업당 하나, 새로 올리면 교체). 작업 소프트 삭제 30일 뒤 첨부 정리 잡이 함께 지운다.
- 진행 보고: `PATCH_BUILT`에 `patchEmpty`(변경 없음 여부)와 파일 개수.
- 내려받기: `POST /api/tasks/{id}/patch/download-link`(등록자·관리자) → 기존 1회용 토큰(60초) 주소. 토큰 저장소는 산출물과 같이 쓰되 어느 파일인지 구분한다.
- 건너뛰기: `POST /api/tasks/{id}/close/skip-patch`(관리자, 상태 종료실패, `PATCH_BUILT` 미완료일 때) → 모드 `SKIPPED` 후 종료 재큐. 병합 전이면 기존 "종료 취소"도 그대로 쓸 수 있다.
- 응답: 작업 목록·상세 응답의 `close`에 `patchMode`와 `patch { name, sizeBytes, fileCount, empty, uploadedAt }`.
- stale 판정: 패치 모드가 REQUIRED이고 `PATCH_BUILT` 전인 종료는 `app.task.close-patch-stale-threshold-minutes`(기본 110 = 종료 60 + 빌드 20×2 + 여유 10)로 본다. 빌드 상한은 워커 설정이라 두 yml에 서로를 가리키는 주석을 둔다(배포 판정 70분과 같은 방식).

## 9. DB (V43)

`com.task`: `close_patch_mode`(VARCHAR 20), `patch_base_sha`(VARCHAR 40), `patch_name`(VARCHAR 255), `patch_size`(BIGINT), `patch_sha256`(VARCHAR 64), `patch_file_count`(INT), `patch_empty`(BOOLEAN), `patch_uploaded_at`(TIMESTAMP).
`com.repo_catalog`: `patch_enabled`(BOOLEAN NOT NULL DEFAULT false).

## 10. 화면

- 작업 목록(`pages/tasks/index.vue`): 작업종료 줄에
  - 패치 파일이 있으면 `부분 패치` 버튼(누르면 바로 내려받기, 2초 재클릭 방지 — 목록에는 지금 내려받기 코드가 없으므로 상세 화면의 산출물 내려받기 로직을 공용으로 빼서 쓴다. 데스크톱 카드·모바일 카드 둘 다).
  - `patch_empty`면 `변경 없음` 표시(버튼 아님).
  - 모드 null·SKIPPED면 아무것도 없음.
- 작업 상세(`pages/tasks/[id].vue`): 종료 단계 목록에 "부분 패치" 단계, 같은 버튼, 종료실패 + 패치 단계 미완료일 때 관리자에게 `패치 없이 마무리`.
- 카탈로그 관리(`pages/admin/repo-catalog.vue`): `부분 패치 만들기` 체크(미리 빌드 명령이 비면 비활성 + 안내).

## 11. 배포·운영

- 순서: 워커(이 PC — 종료를 받는 워커) → API(V43, 스위치 꺼진 채) → 프론트 → `public.env`에 `CLOSE_PATCH_ENABLED=true` → 카탈로그에서 레포 켜기. 원격 워커 2대는 종료를 받지 않지만 claim 응답에 새 필드가 생기므로 모르는 필드를 무시하는지 확인한다.
- 종료 시간이 늘어난다: 첫 패치는 빌드 2번, 같은 레포의 이어지는 종료는 1번(§6.5). 그동안 시험 배포는 떠 있다(패치가 배포 중지보다 앞).
- 패치에 쓰는 빌드 = 카탈로그 미리 빌드 명령 그대로다(`-Pdev` 같은 프로파일 포함). 즉 종료 산출물(전체 WAR)과 같은 조건의 빌드에서 나온 차이다.
- CLAUDE.md 종료 문단에 이 기능을 더한다.

## 12. 시험

- 비교기 단위 시험: 추가·변경·삭제, 내부 클래스, 중첩 jar(시각만 다름 = 같음, 항목 하나 다름 = 통째 포함), 무시 패턴, 묶음(war 2개) 폴더 나누기, 변경 없음.
- 이름 규칙, 대상 판정, 단계 순서·재시도(패치 단계부터 다시), 건너뛰기, 업로드·내려받기 권한, stale 판정.
- 실제 레포 확인: 같은 커밋 두 번 빌드 차이 0, 자바 한 파일 고친 작업에서 기대한 `.class`만 나오는지.

## 13. 작성자 판단(사용자가 직접 정하지 않은 것)

1. 전역 스위치 `CLOSE_PATCH_ENABLED`를 둔다(단계적 반영).
2. `DB_WORK` 작업은 패치 대상에서 뺀다.
3. `rebase` 병합이면 병합 전에 종료실패로 막는다. "전" 커밋은 병합 직전 기준 브랜치 끝을 기록해 검증하고, 확인할 수 없으면 패치를 만들지 않고 실패시킨다(§6.1).
11. 전·후 빌드 결과의 구성이 다르거나 "전"이 빌드되지 않으면 단계 실패 — "패치 없이 마무리"로만 끝낸다(§6.2·§6.3).
4. zip 안에서 배포 파일은 `patch/` 아래, 명세·삭제 목록은 맨 위에 둔다.
5. 파일 이름의 날짜 = 패치 만든 날, 제목 정리 규칙(§7).
6. 무시 패턴 기본값(`MANIFEST.MF`, `META-INF/maven/**`).
7. 해시 목록은 워커 PC에 레포당 20개 보관.
8. 패치 빌드는 미리 빌드 명령을 그대로 쓴다(프로파일 포함).
9. 상세 화면에도 같은 버튼을 둔다.
10. 종료 산출물과 달리 "종료 때 다시 빌드"한다(2026-11-04 설계의 비목표와 다른 점 — 패치는 병합 전·후 두 시점의 빌드가 필요해 배포 이미지만으로 만들 수 없다).

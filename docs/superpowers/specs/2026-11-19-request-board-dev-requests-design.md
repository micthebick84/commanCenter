# 요청 게시판 개발 요청(이슈 등록형) · 사이트 추가 설계

- 날짜: 2026-11-19
- 상태: 사용자 검토 대기
- 범위: 백엔드(Java, API 프로파일만) + 프론트엔드(Nuxt). 워커·인터뷰 서비스 변경 없음
- 선행 스펙: `2026-10-19-request-board-design.md`(요청 게시판), `2026-10-24-task-ref-repos-design.md` §4.1(질문 → 작업 등록 선례), `2026-11-03-task-type-db-write-design.md` §4(작업 타입)

## 1. 목적

기술팀은 지금 고객 사이트의 개발 요청을 hive(사내 이슈 트래커)에 올리고, 개발자가 그것을 읽어 Symphony에 작업을 다시 등록한다. 같은 내용을 두 번 옮겨 적는다.

이 기능은 기술팀이 **Symphony 요청 탭에서 hive의 이슈 등록처럼 개발 요청을 직접 올리고**, 관리자가 그 요청을 **버튼 하나로 작업 등록 폼에 옮기게** 한다. hive와는 데이터를 주고받지 않는다.

## 2. 목표 · 비목표 · 반목표

**목표**
- 요청 종류를 **개발 요청 / 사이트 추가** 둘로 바꾼다.
  - 개발 요청: 새 종류. hive 이슈 등록 폼과 비슷한 칸(유형·우선순위·마감일·대상 레포·첨부)을 가진다.
  - 사이트 추가: 지금의 REPO 추가를 **이름만 바꾼 것**. 처리 흐름(GitLab 후보 → 관리자 클릭 → 카탈로그 등록)은 그대로다.
  - 기능 추가·MCP 추가는 새로 올릴 수 없다. 이미 있는 글은 남겨 두고 읽을 수 있다.
- 개발 요청은 **로그인한 사용자 누구나** 목록·상세를 보고 답글을 단다.
- 관리자가 개발 요청 상세에서 **작업으로 등록**을 누르면 작업 등록 창이 요청 내용으로 채워지고, 등록하면 요청과 작업이 서로 연결된다.
- 개발 요청에 올린 첨부는 작업으로 넘어갈 때 작업 첨부로 복사된다.

**비목표 (이번 범위 밖)**
- hive 연동(가져오기·되돌려 쓰기). hive에 서버용 인증이 없어 보류했다.
- 담당자 지정, 지켜보는 사람, AI 보조(제목 생성·설명 다듬기·이슈 나누기).
- 사이트 추가 자동 등록. 관리자 클릭을 유지한다(사용자 결정 2026-11-19).
- 팀 단위 공개. Symphony에는 관리자/일반 사용자 구분만 있다.
- 답글 첨부, 메일·푸시 알림, 사람별 읽음 기록.
- 작업이 끝났을 때 요청 상태를 따라 바꾸는 것. 요청에는 연결된 작업의 현재 상태를 보여 주기만 한다.

**반목표 (이렇게 되면 기능은 돌아가도 실패)**
- 사이트 추가와 예전 기능 추가·MCP 추가 글이 남에게 보이게 되는 것. 전원 공개는 개발 요청에만 적용한다.
- 개발 요청이 사람의 확인 없이 작업이 되는 것. 작업 등록은 관리자가 폼을 보고 누를 때만 일어난다.
- 일반 사용자가 사내 GitLab 프로젝트 목록을 보게 되는 것(선행 스펙의 반목표 유지).
- 개발 요청을 올리려면 레포를 알아야 하는 것. 대상 레포는 선택 칸이다.

## 3. 접근 방식

| | A. 게시판에 종류 추가 | B. 별도 이슈 게시판 | C. 팀 단위 공개 |
|---|---|---|---|
| 내용 | `request_post`에 칸을 더하고 개발 요청만 전원 공개 | 새 테이블·새 화면 | A + netis-auth에서 팀 정보를 받아 같은 팀만 공개 |
| 장점 | 답글·상태·읽음 표시를 그대로 씀. 가장 작다 | 기존 요청과 섞이지 않음 | 팀 밖에 안 보임 |
| 단점 | 종류마다 공개 규칙이 다름 | 답글·상태·배지를 다시 만듦. 탭이 늘어남 | 인증 서버와 토큰까지 고침 |

**A를 택했다**(사용자 결정 2026-11-19). Symphony 사용자가 사내 개발·기술 인력뿐이라 전원 공개가 "기술팀끼리"와 사실상 같다.

| 항목 | 결정 | 출처 |
|---|---|---|
| 연동 | hive 연동 없음. 기술팀이 직접 등록 | 사용자 |
| 종류 | 개발 요청 / 사이트 추가. 기능 추가·MCP 추가는 등록 폼에서 제거 | 사용자 |
| 사이트 추가 | REPO 추가의 이름 변경. 처리는 지금처럼 관리자 클릭 | 사용자 |
| 공개 범위 | 개발 요청은 로그인 사용자 전원이 열람 | 사용자 |
| 답글 | 개발 요청은 누구나 답글 | 사용자 |
| 예전 기능 추가·MCP 추가 글 | 삭제하지 않고 읽기 가능하게 유지, 새 등록만 막음 | 설계자 제안 |
| hive의 프로젝트 칸 | 대상 레포(카탈로그) 선택으로 대체, 선택 칸 | 설계자 제안 |

| 요청에서 만든 작업의 등록자 | 원 요청자 | 사용자 |

| 열린 요청 상한 | 1인당 20건 유지(종류 합산) | 설계자 제안 |
| 첨부 한도 | 작업 첨부와 같음(파일 10개, 파일당 20MB) | 설계자 제안 |

## 5. 화면

### 5.1 `/requests` 목록

```
요청                                            [+ 새 요청]
[ 내 요청 | 전체 개발 요청 ]   종류 ▾  유형 ▾  상태 ▾
────────────────────────────────────────────────────────
[개발 요청][버그] ▲높음  로그인 뒤 대시보드가 비어 있음      접수    11.19  ●
          강원대 · 홍길동 · 마감 11.25 · 📎2 · 💬3
[개발 요청][개발요청] ●보통  장비 성능 수집 화면 추가         처리완료 → 작업 #51 구현중
[사이트 추가]  대구교육청 레포 추가                           검토중   11.18
```

- **내 요청**: 지금과 같다. 본인이 올린 모든 종류.
- **전체 개발 요청**: 모든 사용자의 개발 요청. 일반 사용자에게 새로 생기는 보기다.
- 관리자는 지금처럼 전체(모든 종류)를 본다. 세그먼트는 관리자에게 보이지 않는다.
- 개발 요청 줄에는 유형 칩, 우선순위, 요청자, 대상 레포 별칭, 마감일, 첨부·답글 수, 연결된 작업 번호와 상태가 붙는다. 값이 없는 것은 생략한다.
- 유형 필터는 종류가 개발 요청일 때만 의미가 있다.
- "새 답글" 점(●)은 지금 규칙(요청자·관리자)대로다. 구경하는 사용자에게는 표시하지 않는다.

```
종류      (•) 개발 요청   ( ) 사이트 추가

대상 레포 [ 선택 안 함 ▾ ]        (모르면 비워 두세요)

마감일    [ 날짜 ]

```

- 기본 선택은 개발 요청이다.
- 수정(접수 상태, 작성자만)은 같은 다이얼로그다. 종류는 못 바꾸고, 첨부는 추가·삭제할 수 있다.

### 5.3 `/requests/[id]` 상세 (개발 요청)

- 머리: 종류·유형 칩, 우선순위, 제목, 상태 칩, 요청자, 등록 시각, 마감일, 대상 레포.
- 본문 설명, 첨부 목록(내려받기).
- 연결된 작업이 있으면 `→ 작업 #51 · 구현중`(작업 상세로 이동). 요청자(= 작업 등록자)와 관리자는 링크로, 작업을 볼 권한이 없는 다른 사용자에게는 번호와 상태만 글자로 보인다.
- 답글 스레드. 답글에는 작성자 이름을 보인다(지금은 "요청자/관리자" 두 역할만 구분).
- 관리자 버튼: 상태 변경(지금과 같음), **작업으로 등록**(상태가 접수·검토중이고 연결된 작업이 없을 때).
- 작성자 버튼: 수정·취소(지금 규칙).

### 5.4 작업으로 등록

`작업으로 등록` → `/tasks?fromRequest={id}`. 작업 등록 창이 아래처럼 채워진다(질문 → 작업의 `fromQuestion`과 같은 방식).

| 작업 등록 칸 | 채우는 값 |
|---|---|
| 레포 | 요청의 대상 레포(없으면 비움, 관리자가 고름) |
| 브랜치 | 그 레포의 기본 브랜치(지금 등록 창 동작) |
| 타입 | 유형이 버그면 `BUG_FIX`, 그 밖에는 비움(관리자가 고름) |
| 제목 | 요청 제목 |
| 설명 | 요청 설명 + 끝에 `— 요청 #{id} · 유형 · 우선순위 · 마감일 · 요청자` 한 줄 |
| 안내 | `요청 첨부 N개가 함께 등록됩니다` |

등록 바디에 `sourceRequestId`가 실리고, 서버가 한 트랜잭션에서:
1. 호출자가 관리자인지, 요청이 개발 요청이고 접수·검토중이며 아직 작업이 연결되지 않았는지 확인한다(아니면 403/409).
2. 작업을 만들고 `task.source_request_id`를 기록한다. **작업의 등록자는 넘긴 관리자가 아니라 원 요청자다**(사용자 결정 2026-11-19) — 요청한 사람이 작업을 보고, 배포 결과를 확인 완료(종료 요청)하고, 수정 요청을 내고, 종료 메일을 받는다. 이력에는 `요청 #{id}에서 등록(관리자 {id})`을 남긴다. 요청에서 온 작업은 등록 때 1인당 동시 진행 한도(`user-concurrent-limit`) 검사를 하지 않는다(설계자 판단 — 관리자가 넘기는 시점에 요청자의 한도로 막히지 않게).
3. 요청 첨부를 작업 첨부로 복사한다.
4. 요청에 `task_id`를 기록하고 상태를 처리완료로 바꾸며 시스템 답글 `작업 #{n}으로 등록 — 처리완료`를 남긴다.

**연결된 뒤의 규칙**(설계자 판단)
- 작업이 연결된 요청은 작성자가 취소(삭제)할 수 없다(409). 작업 상세의 출처가 없는 요청을 가리키지 않게 한다.
- 작업이 연결된 요청은 처리완료에서 되돌릴 수 없다(409). 예외: 연결된 작업이 소프트 삭제됐으면 관리자가 검토중으로 되돌릴 수 있고, 그때 `task_id`를 비워 다시 작업으로 등록할 수 있게 한다(시스템 답글 `작업 #{n} 연결 해제`). `task.source_request_id`는 기록으로 남긴다.
- `task.source_request_id`·`request_post.task_id`에는 FK를 걸지 않는다(질문 → 작업의 `source_question_id`와 같다).

**작성자 취소 가드**(설계자 판단): 지금은 관리자 답글이 있으면 취소를 막는다. 개발 요청은 **작성자가 아닌 사람의 답글이 하나라도 있으면** 취소를 막는다 — 남의 답글이 작성자 취소로 함께 지워지지 않게 한다.

작업 상세에는 `↩ 요청 #{id}에서 이어짐`을 보인다. 기능문의처럼 작업이 필요 없는 요청은 관리자가 답글로 답하고 상태만 바꾼다.

## 6. 데이터 (V46)

마이그레이션 번호는 병합 직전 `origin/main`의 가장 큰 번호 + 1로 확정한다.

**`com.request_post` 추가 칸**

| 칸 | 형식 | 뜻 |
|---|---|---|
| `issue_type` | VARCHAR(20) NULL, CHECK | `BUG` 버그 / `DEV` 개발요청 / `INQUIRY` 기능문의. 개발 요청에만 값 |
| `priority` | VARCHAR(10) NULL, CHECK | `HIGH` / `NORMAL` / `LOW`. 개발 요청은 기본 `NORMAL` |
| `due_date` | DATE NULL | 마감일 |
| `target_repo_catalog_id` | BIGINT NULL | 대상 레포. 기존 `repo_catalog_id`(사이트 추가로 등록된 레포)와 뜻이 달라 따로 둔다 |
| `task_id` | BIGINT NULL | 이 요청으로 등록한 작업 |

**종류 값**: `RequestKind`에 `DEV`(개발 요청)를 더하고 `REPO`의 라벨을 "사이트 추가"로 바꾼다. DB 값 `REPO`는 그대로 둔다(기존 행·코드 유지). `FEATURE`·`MCP`는 enum에 남기되 등록 API가 400으로 거절한다.

**`com.request_attachment`(신규)**: `id`, `request_id`, `ordinal`, `original_name`, `stored_path`, `size_bytes`, `mime_type`, `created_at`. 디스크 경로는 `request-{id}/{순번}-{이름}`(작업·질문 첨부와 같은 저장소·같은 이름 규칙).

**`com.task` 추가 칸**: `source_request_id` BIGINT NULL.

## 7. API

| 엔드포인트 | 변경 |
|---|---|
| `POST /api/requests` | multipart(`meta` + `files`)도 받는다. `kind=DEV`면 `issueType` 필수, `priority`·`dueDate`·`targetRepoCatalogId` 선택. `kind=FEATURE|MCP`는 400 |
| `GET /api/requests` | `scope=dev`를 주면 모든 사용자의 개발 요청(인증 사용자 누구나). `issueType` 필터 추가. 응답에 새 칸·요청자 이름·첨부 수·답글 수·연결 작업(번호·상태) |
| `GET /api/requests/{id}` | 개발 요청은 인증 사용자 누구나. 그 밖의 종류는 지금처럼 본인·관리자(아니면 404). 읽음 갱신은 작성자·관리자일 때만 |
| `PUT /api/requests/{id}` | 개발 요청 칸과 첨부 추가·삭제(`removeAttachmentIds`). 작성자·접수 상태 규칙 유지 |
| `POST /api/requests/{id}/comments` | 개발 요청은 인증 사용자 누구나 |
| `GET /api/requests/{id}/attachments/{attId}` | 신규. 상세를 볼 수 있는 사용자만 |
| `POST /api/tasks` | `sourceRequestId` 추가(§5.4). 관리자만 쓸 수 있다 |
| 관리자 API(상태 변경·요약·사이트 추가 후보/등록) | 변경 없음 |

**읽음 규칙**: 작성자도 관리자도 아닌 사용자의 답글은 작성자와 관리자 양쪽에 "새 답글"로 표시된다(두 활동 시각을 모두 갱신). 관리자 배지 집계는 지금 식을 그대로 쓴다.

## 8. 첨부 처리

- 한도·허용 형식·저장 방식은 작업 첨부와 같다(`AttachmentStorage`).
- 요청 첨부는 슬라이드 렌더링을 하지 않는다. 작업으로 복사된 뒤에는 작업 첨부로서 렌더링 큐에 들어간다.
- 정리: 첨부 정리 잡이 `request-{id}` 폴더를 처리완료·반려 뒤 90일(종료 질문과 같은 기간)에 지운다. DB 행은 남기고 정리 뒤 내려받기는 410.
- 요청 취소(삭제) 때는 그 폴더를 바로 지운다.
- 백업 zip에는 첨부 폴더 전체가 들어가므로 따로 손댈 것이 없다.

## 9. 기존 코드와의 접점

- 백엔드: `entity/RequestKind.java`·`RequestPost.java`, `service/RequestBoardService.java`(공개 규칙·읽음), `controller/RequestBoardController.java`, `service/RepoRequestService.java`(문구만 "사이트 추가"), `service/TaskService.java`(`sourceRequestId`, 첨부 복사는 `inheritQuestionAttachments`와 같은 모양), `dto/TaskCreateRequest.java`·`TaskResponse.java`, `service/AttachmentStorage.java`·`AttachmentCleanupJob.java`·`AttachmentCleanupPlanner.java`.
- 프론트: `pages/requests/index.vue`·`[id].vue`, `components/requests/RequestFormDialog.vue`·`RequestThread.vue`, `composables/requestBoard.ts`, `pages/tasks/index.vue`(`fromRequest`), `pages/tasks/[id].vue`·`components/tasks/TaskDetailMobile.vue`(출처 줄), `scripts/hydration-smoke.mjs`(새 API 목).
- 화면 문구에서 "REPO 추가"를 "사이트 추가"로 바꾼다. 이미 남아 있는 시스템 답글의 옛 문구는 고치지 않는다.

## 10. 테스트

- 서비스 단위: 종류별 열람 권한(개발 요청 전원 / 그 밖 본인·관리자 404), 등록 검증(FEATURE·MCP 400, DEV 필수 칸), 제3자 답글의 읽음 갱신, `sourceRequestId` 검증(비관리자 403, 이미 연결 409, 다른 종류 409).
- 통합(Testcontainers, CI): V46, 등록 → 다른 사용자 열람·답글 → 작업으로 등록 → 요청 처리완료·작업 첨부 복사.
- 프론트(vitest): 폼의 종류별 칸, 세그먼트·필터, 상세의 버튼 노출 조건, `fromRequest` 미리 채움.
- 하이드레이션 스모크: `/requests` 새 응답 모양 반영.

## 11. 배포 순서

API(V46) → 프론트(`.output` 재빌드). 워커·인터뷰 서비스는 바꾸지 않는다. 옛 프론트는 새 API와도 동작한다(기능 추가·MCP 추가 등록만 400).

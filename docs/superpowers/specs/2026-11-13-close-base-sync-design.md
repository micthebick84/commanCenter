# 종료 충돌을 Symphony에서 풀기 — 기준 브랜치 반영 회차

2026-11-13 · 계기: 작업 42 종료실패

## 1. 왜 하는가

작업 42(netis-v6.8, MR !10)의 종료가 `충돌: target 브랜치와 충돌합니다`로 실패했다. 같은 커밋에서 갈라진 작업 41(MR !11)이
50초 먼저 병합됐고, 두 작업이 모두 레포 루트 `PLAN.md`를 통째로 다시 썼기 때문이다(코드 충돌 없음).

지금 Symphony에는 이 상황을 화면 안에서 푸는 길이 없다.

- 실패 문구는 "충돌을 해결한 뒤 재시도하세요"인데, 충돌을 풀면 브랜치 끝이 바뀌어 재시도가 `head 불일치`로 거부된다
  (`GitLabMrCloser.merge` — 종료는 배포로 확인한 `task.head_sha`만 병합한다).
- 실제로 되는 길은 `종료 취소` → GitLab에서 손으로 충돌 해결 → `재배포` → 확인 → 종료 승인이고, 충돌 해결은 Symphony 밖이다.
- 수정 요청 회차는 `종료실패`에서 열 수 없고, 작업 브랜치만 받아 오며, 프롬프트가 merge를 금지한다.

같은 레포에서 두 작업이 동시에 진행되면 다시 난다(이 레포 MR 11개 중 6개가 `PLAN.md`를 바꿨다). 코드 충돌도 같은 모양으로 막힌다.

같은 날 첫 실패는 다른 원인이었다: `병합 거부(checking) (HTTP 422)`. 기준 브랜치가 막 바뀌어 GitLab이 병합 가능 여부를
다시 계산하는 중이었다. 충돌이 없는 작업도 다른 작업 병합 직후에 종료하면 같은 실패가 난다.

## 2. 목표·하지 않는 것

**목표**

1. 관리자가 병합 전 `종료실패`에서 버튼 하나로 작업 브랜치에 기준 브랜치를 반영한다. 충돌이 있으면 Claude 세션이 푼다.
2. 반영 뒤에는 자동 재배포하고, 확인·종료 승인을 다시 받는다 — **배포로 확인한 커밋만 병합한다는 규칙을 유지한다.**
3. GitLab이 병합 가능 여부를 계산하는 동안에는 잠깐 기다렸다가 판단한다.
4. 충돌·head 불일치 실패 문구가 실제로 되는 다음 행동을 안내한다.

**하지 않는 것**

- 종료 요청·승인 때 충돌 미리 확인, 같은 레포 작업 병합 시 열린 작업에 경고(조기 감지) — 다음에.
- 구현 세션이 `PLAN.md` 같은 공용 기록 파일을 통째로 다시 쓰지 않게 하기(예방) — 다음에.
- `종료실패` 밖(배포완료 등)에서 미리 기준 브랜치 반영하기 — 같은 회차를 쓰면 쉽게 넓힐 수 있지만 이번엔 넣지 않는다.
- 재배포 뒤 종료를 자동으로 다시 시작하기.

**해서는 안 되는 것**

- 아무도 확인하지 않은 커밋이 기준 브랜치에 병합되는 것(종료 단계 안에서 바로 풀고 병합하기).
- force push, rebase(작업 브랜치의 기존 커밋을 바꾸는 것).
- 충돌과 상관없는 파일을 고치는 것.

## 3. 검토한 방식

| 방식 | 내용 | 판단 |
|---|---|---|
| 1. 기준 브랜치 반영 회차 | 수정 요청 회차의 변형. 워커가 작업 브랜치에 기준 브랜치를 병합하고 충돌만 Claude가 푼다 → 이어서 push → 자동 재배포 | **선택(사용자, 2026-11-13)** — 코드 충돌까지 풀리고 검증된 회차 흐름(같은 브랜치 worktree·이어서 push·자동 재배포·늦은 보고 판정·GC 보호)을 그대로 쓴다. API·워커·화면을 모두 바꾸고 DB 칸이 늘어난다 |
| 2. 종료 단계 안에서 바로 해결 | 종료 워커가 충돌을 만나면 그 자리에서 풀고 병합 | 제외 — 확인 안 된 커밋이 병합된다 |
| 3. 규칙 기반 자동 해결 | 정해 둔 파일만 한쪽으로 덮고 나머지 충돌은 실패 | 제외 — 문서 충돌만 풀리고 코드 충돌은 여전히 GitLab에서 손으로 |

문서만 충돌했을 때 재배포·재확인을 생략하는 안도 검토했으나 넣지 않는다(사용자 확인: 추천안대로). 재배포는 자동이라 관리자
부담은 확인 한 번이다.

## 4. 흐름

```
[종료실패](병합 전) ──(관리자: 기준 브랜치 반영)──→ [구현대기](반영 회차) ──(워커 claim)──→ [구현중]
   [구현중] ──┬─ 반영할 것 없음 ───────────────────────→ 직전 상태(배포완료|배포중단됨|PR생성)   (회차 닫힘: NO_CHANGE)
              ├─ 병합 성공(충돌 없음 또는 Claude가 해결) → push
              │     ├─ 배포한 적 있는 작업 → 자동 [배포대기] → [배포중] → [배포완료|배포실패] (회차 닫힘 — 수정 회차와 같다)
              │     └─ 배포한 적 없는 DB 작업 → [PR생성]                                      (회차 닫힘: SYNCED)
              └─ 실패 → [구현실패] ──(관리자 구현 재시도)──→ [구현대기](같은 회차)
                                   └─(관리자 반영 중단)──→ 직전 상태                          (회차 닫힘: ABORTED)
```

- "직전 상태"는 종료 요청 직전 상태다 — `TaskCloseService.statusBeforeReview`가 주는 값을 회차 기록의 `from_status`에 박제한다.
- 반영 뒤에는 보통 길로 다시 종료한다: 등록자 확인 완료 → 관리자 종료 승인.
- 작업 42에 대입하면: `기준 브랜치 반영` → 워커가 `main` 병합 → `PLAN.md` 충돌을 Claude가 해결 → push → 자동 재배포 →
  `배포완료` → 확인 → 종료 승인.

## 5. API

### 5.1 데이터 (V45 — 병합 직전 `origin/main`의 가장 큰 번호 + 1로 확정)

`com.task_fix_request`에 칸 하나:

- `kind VARCHAR(20) NOT NULL DEFAULT 'FIX'` + 이름 붙인 CHECK(`FIX`, `BASE_SYNC`). 기존 행은 `FIX`.

`BASE_SYNC` 행이 쓰는 값:

| 칸 | 값 |
|---|---|
| `body` | 빈 문자열이 안 되면 고정 문구 `기준 브랜치 {base} 반영` (builder 판단) |
| `status` | 만들 때 바로 `APPROVED`(승인 단계 없음 — 관리자만 연다) |
| `round` | 그 작업의 `BASE_SYNC` 중 몇 번째인지(1부터) |
| `implementation_mode` | `DIRECT` 고정 |
| `from_status` | 종료 요청 직전 상태(`배포완료`·`배포중단됨`·`PR생성`) |
| `outcome` | 기존 `DEPLOYED`·`DEPLOY_FAILED`·`ABORTED` + 새 값 `NO_CHANGE`·`SYNCED`(outcome에 CHECK가 있으면 같이 넓힌다) |

`task.active_fix_request_id`는 그대로 쓴다 — 열린 반영 회차도 "열린 회차"다. 그래서 회차가 열린 동안의 기존 보호(종료 요청·
재배포·중지·두 번째 요청 409, 소프트 삭제 금지, 배포 컨테이너 GC 보호)가 그대로 적용된다.

### 5.2 열기 — `POST /api/tasks/{id}/close/sync-base` (관리자)

조건(아니면 409, 사유 문구 포함):

- 상태가 `종료실패`이고 `close_progress`에 `MERGED`가 없다(= `종료 취소`가 되는 조건과 같다).
- 열린 회차가 없다.
- `head_branch`·`head_sha`가 있고 `head_branch`가 기준 브랜치와 다르다(수정 요청과 같은 검사).
- 이 작업의 `BASE_SYNC` 회차가 상한 미만이다 — `app.task.base-sync-max-rounds`(기본 3, 중단·변경 없음 포함해 센다).
  수정 요청 상한(`fix-request-max-rounds`)과는 따로 센다 — 서로 깎지 않는다.

한 트랜잭션에서:

1. `종료 취소`가 하는 정리(실패 사유·`close_progress`·`close_patch_mode` 비움).
2. `BASE_SYNC` 회차 기록 저장 → `active_fix_request_id` 설정, 수정 회차 시작 때와 같은 칸 정리(`startRound`).
3. `구현대기`로 전이, 이력 `종료 취소(병합 전) → 기준 브랜치 반영 {n}회차 → 구현대기`.

`close_artifact_mode`는 `종료 취소`가 하는 대로 둔다(다음 종료 승인 때 다시 정해지는지 builder가 확인).

### 5.3 수정 요청 쪽에서 `kind`를 가르는 곳

- 수정 요청 상한 계산(`countByTaskIdAndStatus(APPROVED)`)은 `kind=FIX`만 센다. 화면 `n/3`(`fixViewOf`)도 같다.
- 회차 이름(`FixRounds.label`): `FIX`는 지금처럼 `수정 n회차`, `BASE_SYNC`는 `기준 브랜치 반영 n회차`. 회차를 닫는 이력 문구
  (`(수정 n회차 닫힘)` 등)가 이 이름을 쓴다.
- 이전 회차 본문(`previousBodies`)·`새 작업으로 등록` 안내 판단에 `BASE_SYNC` 행이 섞이지 않게 한다.
- `GET /api/tasks/{id}/fix-requests` 응답에 `kind`를 싣는다. `TaskResponse.FixView`에 열린 회차의 `kind`를 싣는다.

### 5.4 claim

- 구현 claim의 `implementation.fix`(`FixRoundSpec`)에 `kind`를 싣는다(`FIX`는 지금과 같은 바디 + `kind`).
- **구버전 워커 막기**: 새 워커는 `supports=…,baseSync`를 보낸다. `baseSync`가 없는 요청에는 `BASE_SYNC` 회차가 열린
  구현대기를 넘기지 않는다(`WorkerCapabilities`·`findClaimableAmong` — `fixRounds` 가드와 같은 방식). 구버전 워커는 `kind`를
  버리고 빈 수정 요청으로 Claude를 돌리기 때문이다. 원격 워커 2대도 구현을 받으므로 대상이다.
- 구현 상한·stale 판정은 회차 방식(DIRECT) 기준 — 지금 회차 코드 그대로.

### 5.5 결과 보고 (`recordFixRoundImplementationResult` 갈래)

늦은 보고 판정(작업 시도 번호 + 회차 안 시도 번호 + 회차 요청 id)은 그대로.

| 보고 | `FIX` (지금) | `BASE_SYNC` |
|---|---|---|
| 성공, `headSha`가 기록과 다름 | `head_sha` 갱신 → 자동 `배포대기` | 배포한 적 있으면 같다. **배포한 적 없는 작업**(`deployUrl`·`deployedAt` 둘 다 없음 — DB 작업의 PR생성 종료)은 `head_sha` 갱신 → `PR생성`, 회차 `SYNCED`로 닫음 |
| 성공, `headSha`가 기록과 같음 | (해당 없음) | 반영할 것이 없었다 → `from_status`로, 회차 `NO_CHANGE`로 닫음, 이력 `기준 브랜치가 이미 반영돼 있음 → {상태}` |
| 실패 | `구현실패`, `head_sha`를 보고된 브랜치 끝으로 맞춤(`WorkerService` 회차 실패 갈래) | `구현실패`. **`head_sha`는 바꾸지 않는다** — 보고에 실린 브랜치 끝을 무시한다 |

`BASE_SYNC` 실패가 `head_sha`를 건드리지 않는 이유: 사람이 브랜치에 직접 push한 상태(브랜치 끝 ≠ 기록)에서 회차가 실패하고
중단하면 작업이 `배포완료`로 돌아가는데, 그때 `head_sha`가 브랜치 끝으로 바뀌어 있으면 배포로 확인한 적 없는 커밋이 다음
종료에서 병합된다. 바꾸지 않으면 다음 종료는 `head 불일치`로 거부된다(맞는 동작).

"기록과 같음/다름"은 **회차를 열 때의 `task.head_sha`** 와 보고의 `headSha`를 비교한다. 사람이 push한 커밋 위에서 기준
브랜치가 이미 반영돼 있던 경우는 "다름"이므로 재배포 길로 간다(그 커밋이 재배포로 확인된다) — `NO_CHANGE`는 브랜치가
확인된 커밋 그대로일 때만이다.

복귀 상태 판정은 `BASE_SYNC` 전용으로 둔다: `from_status`가 `배포완료`·`배포중단됨`·`PR생성` 중 하나면 그 값, 아니면
`TaskCloseService.statusBeforeReview`와 같은 대체 규칙(배포한 적 없는 DB 작업은 `PR생성`, 그 밖은 `배포중단됨`). 수정 요청의
`statusBeforeRequest`는 `PR생성`을 모르는 값으로 보고 `배포중단됨`으로 돌리므로 그대로 쓰면 안 된다.

### 5.6 실패한 반영 회차에서 빠져나오기

- `구현 재시도`: 기존 `requeueFixRound` 그대로(같은 회차·같은 브랜치). 방식 선택은 받지 않는다(DIRECT 고정).
- `반영 중단` = 기존 `POST …/fix-requests/abort`가 `BASE_SYNC`면 다르게 끝낸다: 회차 `ABORTED`, **`from_status`로 복귀**
  (수정 중단처럼 `PR생성`·`배포중지대기`로 보내지 않는다 — 반영 회차는 실패 때 브랜치에 아무것도 올리지 않고 `head_sha`도
  바꾸지 않아(5.5) 떠 있는 배포가 여전히 `head_sha`와 같다). 이력 `기준 브랜치 반영 n회차 중단 → {상태}`.
- 재기동 재큐·깨진 회차 처리(`TaskRecovery`·`failBrokenFixRound`)는 kind와 무관하게 지금 규칙.

## 6. 워커

`WorkerMainLoop.implementFixRound` 앞에서 `fix.kind`가 `BASE_SYNC`면 새 길(`syncBaseRound`)로 간다.

1. 브랜치 검사(`isUsableFixBranch`) — 기존과 같다.
2. 레포 락 안에서 작업 브랜치와 **기준 브랜치**를 fetch한다. 캐시의 HEAD는 건드리지 않는다. 기준 브랜치의 원격 추적 ref를
   갱신해도 되는지, 전용 이름공간에 받을지는 builder가 `GitRepoCache`의 기존 규칙에 맞춰 정한다.
   - **공통 조상**: 캐시는 `--depth=1` clone이라 두 브랜치의 공통 조상이 없을 수 있다. 두 브랜치를 깊이 50으로 받아
     `git merge-base`를 확인하고, 없으면 깊이 500으로 한 번 더 받는다(참조 커밋 받기 `prepareRefCommitUnderLock`의 50→500
     선례와 같다). **unshallow는 하지 않는다.** 그래도 공통 조상이 없으면 Claude 없이 실패:
     `기준 브랜치 반영 n회차: 공통 조상을 찾지 못함(이력 500커밋 초과) — GitLab에서 직접 해결하세요`.
   - 공통 조상 없이 `git merge`를 돌리지 않는다(무관한 이력 병합·"이미 반영됨" 오판 방지).
3. 작업 브랜치 끝에 detached worktree(`createOnBranch`), `tip` 확인. `tip`이 기록된 `head_sha`와 다르면(사람이 push) 그 위에서
   진행하고 구현 로그에 남긴다(기존 회차와 같다).
4. `git merge --no-ff --no-commit <기준 브랜치 끝>`(워커 git 작성자, 무프롬프트).
   - **이미 반영됨**(기준 브랜치 끝이 `tip`의 조상): push 없이 성공 보고(`headSha = tip`). Claude 없음.
   - **충돌 없음**: 병합 커밋 → 이어서 push → 성공 보고. Claude 없음.
   - **충돌**: 충돌 파일 목록을 뽑아 5로.
5. Claude 세션(작업의 모델·effort, 상한은 claim의 구현 상한, 작업이 고른 MCP·DB 서버·참조 repo·목업 없음 — 충돌 해결에
   필요 없고 SQL을 실행하면 안 된다. 워커가 모든 세션에 늘 붙이는 기본 MCP 합본은 그대로다 — 그것까지 떼려면 실행기를
   고쳐야 해서 이번엔 하지 않는다). 프롬프트(`BaseSyncPrompts`, 새 파일)의 요지:
   - 지금 디렉터리는 작업 브랜치에 기준 브랜치를 병합하다 멈춘 상태다. 충돌 파일은 다음과 같다(목록).
   - 충돌 표식이 있는 곳만 고친다. 양쪽 변경의 의도를 모두 살린다 — 이 작업의 변경(제목·요건·확정 계획을 참고로 준다)과 기준
     브랜치에 먼저 들어온 변경 둘 다.
   - 작업 기록 문서(`PLAN.md`처럼 작업마다 통째로 다시 쓰는 파일)는 한쪽을 버리지 말고, 기준 브랜치 쪽 내용을 남기고 이 작업
     내용을 덧붙이는 식으로 합친다.
   - 충돌하지 않은 파일은 건드리지 않는다. 리팩터링·포맷 정리 금지.
   - `git add`는 해도 되지만 commit·push·rebase·reset·`merge --abort`·checkout·switch는 하지 않는다.
   - 어느 쪽을 살려야 할지 판단할 수 없으면 고치지 말고 이유를 출력한다.
6. 워커가 결과를 검사한다.
   - 병합 안 된 경로가 남았거나(`git diff --name-only --diff-filter=U`), 충돌했던 파일에 충돌 표식(`<<<<<<<`·`=======`·
     `>>>>>>>` 줄)이 남았으면 실패.
   - 충돌했던 파일 밖에 워커가 모르는 변경이 생겼으면 실패(임시 파일 exclude 대상은 제외).
7. 병합 커밋(`merge: 기준 브랜치 {base} 반영 — {제목}` + `task #{id}`) → **이어서 push만**(force 없음) → 성공 보고(같은
   브랜치·새 `headSha`·구현 로그에 충돌 파일 목록과 Claude 출력). PR/MR은 새로 만들지 않는다.

실패 처리:

- 어느 단계든 실패하면 `구현실패` 보고, 사유는 `기준 브랜치 반영 n회차: …`(예: `충돌 해결 실패 — 남은 충돌 파일: a, b`).
- **wip 커밋을 올리지 않는다**(반쯤 병합된 상태를 브랜치에 남기지 않는다). 보고의 `headSha`는 `tip`.
- worktree는 실패면 디버그용으로 남기고(기존 정리 잡이 7일 뒤 삭제) 성공이면 지운다. 재시도는 worktree를 새로 만든다 —
  남은 것이 있으면 기존 회차 재시도가 하는 대로 치운다.
- push가 거절되면(그 사이 사람이 push) 기존 회차와 같은 사유 문구(`PUSH_REJECTED_NOTE`) — 재시도는 새 끝에서 다시 병합한다.

DB 스크립트 파일·배포 env 목록·리뷰 절·타입 절은 이 길에서 다루지 않는다(병합이 양쪽 파일을 그대로 가져온다).

워커 claim URL: `supports=refRepos,fixRounds,dbWrite,mockups,baseSync`.

## 7. 병합 가능 여부 계산 기다리기 (`GitLabMrCloser.merge`)

- MR을 읽었을 때 `detailed_merge_status`가 "아직 계산 중"을 뜻하는 값이면(작업 42에서 본 값은 `checking`; `unchecked`·
  `preparing` 등 같은 뜻의 값은 **구현 때 이 GitLab 버전의 API 문서로 확인**) 짧게 기다렸다 다시 읽는다 — 2초 간격 최대 10회
  (기존 `Sleeper` 주입 사용, 상수).
- 끝내 계산이 안 끝나면 병합 PUT 없이 거부: `병합 가능 여부 확인 중 — 잠시 뒤 재시도하세요`(draft 해제 전이라 제목 원복 불필요).
- MR이 Draft면 `detailed_merge_status`가 `draft_status`로 덮여 계산 중인지 안 보일 수 있다(작업 42가 그랬다 — 지금 코드
  주석도 같은 점을 적고 있다). 이 경우 대기 판단을 어디서 할지(draft 해제 뒤 한 번 더 읽기 등)는 GitLab 문서 확인과 함께
  builder가 정한다 — 어느 쪽이든 거부로 끝나면 제목을 원복한다.
- 계산이 끝난 뒤의 판단(충돌·target 없음·draft 해제·PUT)은 지금 그대로.
- PUT 뒤 거부 사유 분류(`classify`)에도 같은 값들을 `병합 가능 여부 확인 중`으로 넣는다(`병합 거부(checking)` 대신).
- GitHub(`GitHubPrCloser`)는 이번에 손대지 않는다 — 같은 종류의 창(`mergeable=null`)이 있는지만 builder가 확인해 있으면
  TODOS에 적는다.

## 12. 알아 둘 위험

- Claude가 충돌을 잘못 합칠 수 있다. 방어는 재배포 뒤 사람의 확인 한 번이다 — 확인하는 사람이 충돌 파일을 알 수 있게 구현
  로그·회차 이력에 충돌 파일 목록을 남긴다.
- 반영 회차가 도는 동안 기준 브랜치에 또 병합이 들어오면 다음 종료에서 다시 충돌할 수 있다. 그때는 다시 누른다(상한 3회).
- 재배포는 저장된 env로 돈다. 기준 브랜치에서 들어온 변경이 새 env를 요구하면 배포실패가 될 수 있다(보통 재배포로 푼다).
- 반영으로 브랜치에 기준 브랜치의 변경이 들어오므로, 재배포된 화면에는 다른 작업의 변경도 함께 보인다(병합 뒤 모습과 같다).

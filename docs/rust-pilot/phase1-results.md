# Rust 워커 1단계 — 격리 끝-끝 확인과 측정 (2026-11-28)

스펙 `docs/superpowers/specs/2026-11-28-rust-worker-skeleton-design.md` §12.4·§13. 커밋 `c067390` 기준, 이 PC(Windows 11, `x86_64-pc-windows-gnu`, Rust 1.100.1)에서 실행했다.
라이브 API·라이브 DB·라이브 폴더는 건드리지 않았다(아래 "격리 방법").

## 격리 방법

- **임시 PostgreSQL**: `initdb`로 임시 폴더에 새 클러스터를 만들어 다른 포트(55432)로 띄웠다. 라이브 DB 서버에는 데이터베이스조차 만들지 않았다.
- **임시 API**: worktree에서 만든 jar를 다른 포트(18090)로, 환경을 비우고(`env -i`) 필요한 값만 준 채 띄웠다. 데이터소스 주소는 명령줄로 임시 DB를 지정하고, `user.home`도 임시 폴더로 돌렸다. 정리 잡 두 개·슬라이드 렌더링·앱 로그 중계를 끄고 분석 정체 회수 상한을 30분으로 늘렸다.
- **확인 순서**: 기동 로그의 Flyway `Database: jdbc:postgresql://127.0.0.1:55432/…` 줄을 먼저 확인한 뒤에야 작업을 넣고 워커를 붙였다.
- **Rust 워커**: `REPOS_DIR`·`DEAD_LETTER_DIR`를 임시 폴더로 주고 임시 API에 붙였다. claude 로그인은 워커가 평소 쓰는 토큰 환경변수를 그대로 썼다.
- 끝난 뒤 임시 API·임시 DB·임시 폴더·프로세스를 모두 지웠고, 라이브 서비스 세 개(auth·api·worker)의 pid가 그대로임을 확인했다.

## 끝-끝 결과

`작업대기` 작업 두 건을 SQL로 넣었다(작은 공개 저장소, 분석만).

| 작업 | 기대 | 결과 |
|---|---|---|
| 정상 브랜치 | 분석완료 | `분석완료`. 분석 결과 1,540자·작업 목록 2건 저장, 단계별 사용량 한 줄 누적(비용 $0.068, 출력 1,472토큰), 경고 없음 |
| 없는 브랜치 | 분석실패 + 사유 | `분석실패`. 사유 `레포 fetch 실패: git failed (128): fatal: couldn't find remote ref refs/heads/…` |

- 기동 알림 → claim → git 캐시 준비(잠금 파일·`.last-used` 생성) → claude 실행 → 파싱 → 보고가 한 번에 통과했다. 정상 건은 claim에서 보고까지 40초였고 그 가운데 claude가 38.9초다.
- 하트비트 행: 호스트 이름, 버전, 로그인 판정(`ENV_TOKEN`, 정상), MCP 서버 5개, 유실·포기 보고 0건.
- Rust 워커 로그에 경고·오류 0줄, 인증 URL·토큰 0건.
- 워커별 MCP 합본 파일은 `REPOS_DIR`의 형제 위치에 워커 ID 이름으로 생겼다.

## 기동·정지 스크립트 흐름

`start-public.ps1`의 실제 함수(`Get-ServiceExe`·`Start-Service-Proc`·`Wait-Log`·`Register-Service`·`Remove-OldExes`)와 `public-proc.ps1`의 `Find-AppPid`·`Test-ServiceAlive`·`Stop-ServiceRecord`를 임시 실행 폴더로 돌렸다(라이브 스크립트 자체는 실행하지 않았다).

| 단계 | 결과 |
|---|---|
| 빌드 → `netis-worker-rs-<sha7>.exe` 사본 | 생성됨. 깨끗한 트리에서 다시 부르면 같은 사본을 재사용(빌드 없음) |
| 기동 → 준비 줄 대기 | `worker-rs started:` 줄로 준비 판정 |
| 기록 | `worker-rs.json`에 래퍼 pid와 실제 exe pid·이미지 이름이 기록됨 |
| 정지 | exe와 래퍼가 모두 내려가고 남은 프로세스 0 |
| 잘못된 설정(`WORKER_KINDS=DEPLOY`) | `worker-rs fatal:` 줄로 2초 안에 실패 판정 |
| 정리 | 실행 중·최근 사본 유지, 이전 로그는 `logs\`로 보관 |

## 측정

| 항목 | Rust 워커 | Java 워커(라이브, 참고) |
|---|---|---|
| 확보 메모리(private bytes) | **2.4 MB** | 385 MB |
| 작업 집합(working set) | 8.3 MB | 94 MB |
| 스레드 | 5 | 47 |
| 실행 파일 | 1.9 MB(exe 하나) | jar 119 MB + JDK |
| 기동 → 준비 | 1초 미만 | 약 5초 |

- Rust 수치는 기동 약 5분 뒤, 분석 두 건을 처리한 다음의 값이다. **스펙이 정한 "켠 지 1시간 뒤" 수치는 라이브에서 켠 뒤에 잰다.**
- Java 워커는 종류 전부와 PC 단위 주기 작업을 맡고 있어 하는 일이 다르다. 두 숫자는 "같은 일의 비교"가 아니라 "상주 비용의 크기" 비교다.
- 빌드 시간: 릴리스 전체 빌드 약 30초, `main.rs`만 고친 뒤 재빌드 24초(링크 시간 최적화 설정 영향 — 줄일 여지가 있다).
- 코드량: Rust `src` 3,753줄(단위 시험 포함), 통합 시험과 시험용 도우미 3,136줄. 같은 범위의 Java 파일 13개는 2,712줄(파일 전체 기준이고 일부 메서드만 옮겼다)이다. **줄 수는 줄지 않았다** — 이득은 메모리·기동 시간·배포물 크기이고, 대가는 Java와 Rust 두 구현을 계약 파일로 맞춰 유지하는 일이다.
- 시험: Rust 시험 167개(`cargo test --features test-bins`), Java 계약 시험 7개, 스크립트 시험 98개.

| 기준 | 상태 |
|---|---|
| 상주 메모리 30MB 이하 | 통과(2.4 MB) — 1시간 수치는 라이브에서 재확인 |
| 계약 시험이 양쪽 CI에서 통과 | 이 PC에서는 통과. **CI(특히 리눅스·Windows 러너)는 PR을 올려야 확인된다** |
| 잠금 호환 | 통과(Windows에서 Java ↔ Rust 서로 배타, 실측) |
| 격리 끝-끝 | 통과 |
| 라이브에서 기동·정지 3회 무사고 | **아직 안 함** — 라이브에서 켜는 것은 별도 승인 사항 |

## 확인하지 못한 것

- 리눅스에서의 동작 전부(시험은 `cfg`로 갈라 두었지만 실행해 보지 못했다).
- GitHub Windows 러너에서 GNU 타깃 링크가 되는지.
- 실제 라이브 스케줄 작업 경로로 켰을 때의 동작(위 스크립트 확인은 같은 함수를 임시 폴더로 돌린 것이다).
- 유실 보고 재전송은 가짜 API 시험으로만 확인했다(실제 API를 내렸다 올리는 시험은 하지 않았다).

## 측정 뒤에 바뀐 것과 다시 확인한 것

위 표의 수치는 커밋 `c067390`에서 잰 것이다. 그 뒤 전체 검토에서 나온 지적을 고쳤다(커밋 `3988a6c`까지): API 리다이렉트를 따라가지 않음, 로그인 판정 전에는 상태를 보내지 않음, 비밀 값이 든 구조체의 디버그 출력 가림, 구현하지 않은 종류의 작업을 받으면 워커를 멈춤, 프로세스 강제 종료 대기에 상한, 시작 스크립트에서 worker-rs를 인터뷰 서비스 뒤로 옮기고 빌드 15분 상한·워커 이름 충돌 검사 추가, 켠 적이 없으면 정지 때 아무것도 찍지 않음. 이 수정은 프로세스 실행·API 호출·실행 루프를 건드렸으므로 아래를 **최종 커밋에서 다시** 돌렸다.

| 다시 확인한 것 | 결과 |
|---|---|
| 격리 끝-끝(임시 PostgreSQL + 임시 API + 실제 claude) | 통과. 정상 건 `분석완료`(claim → 보고 27초, 분석 결과 1,495자·작업 목록 3건, 사용량 한 줄), 없는 브랜치 건 `분석실패` + 사유. 하트비트 행 정상, 워커 로그 경고·오류 0줄 |
| Rust 시험 / 스크립트 시험 / Java 계약 시험 | 167개 / 98개 / 7개 통과 |
| worker-rs 빌드 → 사본 실행 → 준비 확인 → 정지 → 잘못된 설정 감지(시작 스크립트의 실제 함수, 임시 폴더) | 통과 |
| **기존 Java 서비스 경로**(이 브랜치가 공용 함수 `Invoke-Logged`·정리 함수·프로세스 찾기를 바꿨으므로): jar 빌드 → 사본 실행 → 기동 실패 감지 → 빌드 실패 시 이전 jar로 넘어가지 않음(임시 폴더) | 통과 — jar 실행 전환(#152) 때와 같은 결과 |

실행 파일 크기는 최종 커밋에서 1.95 MB다. 메모리 수치는 다시 재지 않았다(수정이 상주 구조를 바꾸지 않았다).
